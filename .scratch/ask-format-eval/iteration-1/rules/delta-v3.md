
## 补充：让不熟业务的读者一眼看懂（在上面规则之上叠加，冲突时以本节为准）

读这条提问的人懂开发，但没参与这段会话、不熟这个业务。他往往只扫开头几行就决定要不要细读，所以最重要的信息要放在最前面，看不懂的词要当场解释。

1. **第一行写摘要**：`[要拍板]` / `[要信息]` / `[要授权]` 三选一作标签，接一句话：要对方决定什么、你推荐哪项、不答的话会卡在哪或默认怎么走。同一条消息问了几件事，就在这一行列出几件（如「两件事：导入范围、两组模块归属」）。四要素与问题放在这行之后。
2. **业务词当场解释**：读者不在这个项目里就看不懂的词（内部代号、仓库名、环境名、流程阶段名、缩写），首次出现时紧跟括号写一句白话，说清它是什么、在这件事里起什么作用。这类词超过 3 个时，改在摘要行后面放一张术语表（词 / 白话 / 在这个决定里的角色），最多 5 行，只收最承重的。白话从会话记录里找；找不到就写「我不确定」，不编。
3. **关系画出来**：三个以上的仓库、模块、服务或版本互相依赖时，在「差距」或「影响范围」里用缩进树画出依赖关系，放进代码块，只用缩进表达层级，不画方框。
4. **要改的位置列成表**：影响范围里列了三处以上要改的文件、文档或模块时，用表格写「位置 / 现在是什么 / 选了会怎样」。
5. **选项写三样**：每个选项写清「做什么、代价、能不能回退」。哪一样你确实不知道，就不写那一样，不留「未给」「无」之类的占位。
6. **和这次拍板无关的材料往后放**：同一条消息里还要汇报别的结果（如另一项检查的结论），放在问题之后，用分隔线隔开，标题注明「另附」，不要压在问题前面。
