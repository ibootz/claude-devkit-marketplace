# 14: 「上一版」臂的插件目录怎么产出

Type: grilling
Status: resolved
Blocked by: 无

## Question

[缺口里哪些自建、以什么形态](09-build-vs-extend.md) 定了臂由外围脚本编排：每个臂各跑一次 `eval --ablation none`。「改版比上一版」是最常见的对照（[评测要回答哪些问题](07-questions-eval-must-answer.md) 的基线规则），需要一份上一版的插件目录；过去两次都是手工 `git archive` 加手写 `--settings`（见 [仓内历史评测实践盘点](02-prior-eval-practices.md)）。

要决定：

1. 「上一版」怎么认定：被测插件仓 git 历史里 `plugin.json` 的 `version` 上一次变化的提交、上一个已审报告对应的版本、还是用户指定的提交。
2. 快照怎么取：`git archive` 到临时目录、`git worktree`、还是本机插件缓存里的旧版本目录。
3. 「加环境插件」臂的环境插件目录从哪取（本机缓存的当前版本，还是用户指定路径）。
4. 被测插件不在 git 仓里、或首次评测没有上一版时怎么退化（只跑「不装」基线）。

## Answer

2026-10-15 用户原话「全部按推荐」，第一轮五问照推荐定（Q4 与 Jev 不同，见下）。

**前提（由「臂」的定义推出，不另问）**：每个臂在一个临时**组装目录**里跑——被测插件（上一版快照或当前工作目录）、可选的环境插件、`evals/` 并排放；`evals/` 一律取当前版仓里的用例，快照自带的 `evals/` 不用。理由：eval 没有加载额外插件目录的命令行参数，额外插件只能写在用例 `plugins` 字段且须在 containment root 内（[probe/REPORT.md](../probe/REPORT.md#六对工单-09-的影响) 多插件一节）。

1. **「上一版」认定**：被测插件 git 历史（沿 `HEAD`，按改名追踪 `plugin.json`）里，**版本号与工作目录 `plugin.json` 不同的最近一个版本**，取该版本号**被引入的那个提交**。可用 `--base <提交|版本号>` 覆盖。理由：版本号跳号、同号跨多个提交且内容不同、并行分支各自写出同一版本号（本仓 3.27.0），只认版本号会拿到混合态；取引入提交最接近用户升级时拿到的内容，且版本号下的中途修复会落在「当前版 − 上一版」的差里、不会永远评不到。已知代价：尚未升版本就跑时，差里会多出上一个版本自身的改动。
2. **快照方式**：`git archive <提交> <该提交下的插件路径> | tar -x` 解到臂组装目录；插件路径按 `git log --follow` 取当时的值（改名前在旧路径）。只读、不留 worktree 登记。已知代价：被 git 忽略却运行必需的文件会缺——本仓插件没有，他人插件未核实，归 [15](15-preflight-checks.md) 的「被测插件目录结构合法」一并检查。
3. **环境插件**：入参两种都收——`插件名@市场` 按 `~/.claude/plugins/installed_plugins.json` 的 `installPath` 取本机当前版；写路径则用该路径。都拷进臂组装目录，排除运行时文件 `.in_use/`；结果里记下每个环境插件的来源、版本号、`gitCommitSha`（注意它是刷新时市场仓的 HEAD，不是版本引入提交）。
4. **退化**：被测插件不在 git 仓、或历史里没有与当前不同的版本号、或快照失败时，**自动跳过上一版臂，只跑「不装」与「当前版」**，报告首段写明退化原因。新插件首次评测按 [07](07-questions-eval-must-answer.md) 本来就比「不装」，不算退化。退化报告能否作闸门内版本的已审依据，由用户审报告时判断。
5. **改名跨臂**：上一版与当前版 `plugin.json` 的 `name` 不同时，**快照原样不动**；报告标注「跨改名」，并列出判分规则里写了 skill 全名（`插件名:skill名`）、因而跨臂不可比的用例。不改快照的 `name`，避免扭曲旧版行为。

**Jev 分歧**：Q4 Jev 选「自动退化，但退化报告一律不能作闸门已审依据」（置信 0.30）；未采纳，理由是不在 git 仓的插件永远取不到上一版，选它等于其闸门内版本只能走 `eval-skip:`，交由用户审报告时判断更合适。其余四问 Jev 与推荐一致（Q1 0.64、Q2 1.00、Q3 0.69、Q5 1.00）。

**未选**：上一版取该版本号下最后一个提交、取上一份已审报告的提交、每次由用户指定；`git worktree`、本机缓存旧版目录（缓存只留当前版一个目录）；环境插件只收 `插件名@市场` 或只收路径；找不到上一版时中止；改快照 `name`、改名时不跑上一版臂。

**交给其它票**：

- [13](13-result-layout.md)（评测产物与状态落在哪）：每份对照结果要记下——上一版的提交 sha、版本号、取得方式（自动 / `--base`）、是否退化及原因、是否跨改名；当前版的 `HEAD` sha 与工作目录是否有未提交改动；每个环境插件的来源、版本号与 sha。工作目录有未提交改动时产出的报告能否对应到某个版本号、算不算闸门依据，由 13 定。
- [15](15-preflight-checks.md)（跑前检查）：快照与环境插件目录也要过「插件目录结构合法」与 PATH 直达真实 node 两项检查——旧版 hook 同样受 asdf shim 的 exit 126 影响。

**残余不确定**：

- 用例的 `plugins` 字段写相对路径，组装目录布局下由脚本生成还是改写用例，未定，属实施细节。
- 同一 eval 内同时加载两个同名不同版本的插件目录的行为未实测；本决定让每个臂只放被测插件的一个版本，不依赖它。
- `--eval-dir` 指向组装目录之外的用例目录是否可行未实测；本决定改为把 `evals/` 拷进组装目录，不依赖它。

**重开条件**：

- 他人插件普遍依赖构建产物或被忽略文件、`git archive` 快照跑不起来时，重议第 2 条（改为在快照上跑构建步骤，或允许用户提供上一版目录）。
- 退化报告被用户实际当作闸门依据后发现漏判回归时，重议第 4 条（改采 Jev 的选法）。

## Comments

### 2026-10-15 第一轮提问（待答）

已认领。两路子代理补查的事实（本轮核实）：

- `claude plugin eval` 的被测目标是位置参数，目录路径即可，不需要 git 仓或 marketplace；**没有**加载额外插件目录的命令行参数，额外插件只能写在用例的 `plugins` 字段，且必须位于 containment root 内——probe 实测「外层目录并排放多个插件目录 + `evals/`」的布局可行（[probe/REPORT.md](../probe/REPORT.md) 第 146–153 行、`probe/logs/smoke.stderr` 第 5 行）。
- 本机插件缓存每个插件**只留当前版一个目录**，没有旧版；缓存目录混有运行时文件 `.in_use/<pid>`。`installed_plugins.json` 每条记录有 `installPath`、`version`、`gitCommitSha`，`gitCommitSha` 是刷新那一刻市场仓的 HEAD，不是该版本号引入的提交。
- 本仓 git 历史：`version` 会跳号；近 53 个非 merge 提交的 79 条「提交 × 插件」记录里，13 条改了内容没升版本；同一版本号可跨多个提交且内容不同；`7023a8b` 与 `63c2410` 在两条并行分支上各自写出 3.27.0。升版通常与内容改动同提交。
- 2026-10-13 改名后，上一版可能在旧路径、旧名字下（devkit-discipline 4.0.0 之前在 `plugins/working-discipline/`）；`git log --follow` 能追到。
- 本仓插件无构建步骤，不依赖被 git 忽略的文件，不引用插件目录外的文件；他人插件未核实。
- 历史两次手工评测都用 `git archive <commit> <插件路径> | tar -x` 取旧版（wenyan 装置 README 第 67–72 行）。

由已拍板约束直接推出、不另问的：「上一版」臂跑的是**当前版仓里的用例**（臂的定义：同一批用例每个臂各跑一遍），快照自带的 `evals/` 不用。
