# 17: 离线对照的用例从哪来、怎么构造

Type: grilling
Status: resolved
Blocked by: 无

## Question

[评测产物与状态落在哪、什么格式](13-result-layout.md) 定了 AI 起草的用例放草稿区、通过的放 `<plugin>/evals/`；[判分分工与人工介入点](11-judging-and-human-checkpoints.md) 定了草稿要在待审页勾选通过才能跑。用例本身从哪来、怎么造，还没定：

1. **来源**：AI 按被测插件内容编造；从会话复盘的候选里转（[评测范围](06-scope.md) 定了复盘要给离线对照供料，供料形态未定）；复用历史装置里的用例（wenyan、probe 三例）。各占多少、谁先谁后。
2. **会话复盘 → 用例的供料形态**：复盘候选带哪些字段（原始 prompt、上下文片段、违规条款、会话位置），转成 `case.yaml` 时怎么脱敏、怎么裁上下文。
3. **「compact 之后」的回放会话怎么低成本构造**：[缺口里哪些自建、以什么形态](09-build-vs-extend.md) 定了用 `context.history_file` 回放补充；是截取真实 compact 后的会话片段、还是合成一份含 compact 摘要的 jsonl；wenyan 那轮真跑 32 万 token 没做成。
4. **基线已满足的条款**：不装插件时模型本来就会做对的条款，要换诱导 prompt 才测得出差（见 probe 报告「对工单 09 的影响」一节）；诱导用例怎么写、怎么防止过拟合到某一版注入文本。
5. 每个作用方式、每条纪律条款至少几例，与单次 $10、每月 $50 的预算怎么对上。

## Answer

> **2026-10-15 部分覆盖**：用户 2026-10-15 撤销美元花费上限（原话「由于我使用的是订阅 测评额度不适用 可以去掉 避免因为额度干扰了测评的质量」），随后拍板四项连带决定（原话「Q17 用最贵那一档 比如Fable模型 其他按照建议」），记录见 [08](08-cadence-and-budget.md) Comments。作废：第 7 条「每次只跑改动触及的用例、余下预算按最久没跑轮换」。现行：**每次离线对照全量跑所有已通过的用例**，每例每臂 3 次不变；每条款 1 例、基线已满足的另加 2 例诱导用例不变；用户审阅时间由待审页「每页 ≤ 10 项、超出抽样」兜住。

2026-10-15 用户两轮拍板，原话均为「全部按推荐」。Jev（jev-1.13.0）八题均与推荐一致。术语见 `CONTEXT.md`「插件评测」节（条款清单、复盘候选、基线已满足、回归守护用例、诱导用例）。

**1. 来源与先后**：冷启动由 AI 按条款清单起草为主；会话复盘的候选随复盘逐步补充、替换编出来的用例。历史素材：probe 的派发带 `model`、并发检索两例转草稿；待拍板不弹框例不迁（依赖 `AskUserQuestion`，归会话复盘）；zh-disambiguate 的 3 例（skill-creator 格式）改写成 eval 格式进草稿；wenyan 10 场景只作写法参考，不迁。所有来源一律先进 `drafts/`、勾选通过才跑（见 [判分分工与人工介入点](11-judging-and-human-checkpoints.md)）。

**2. 条款清单**：AI 从被测插件注入文本抽条款，每条一个稳定 id（不用注入里会漂移的章节编号），存 `plugin-evals/<plugin>/` 下一份清单文件；用户在待审页整份确认一次（算 1 项）。用例用 `tags` 挂条款 id。

**3. 复盘 → 用例的供料**：
- 复盘候选只存指针与信号：会话 id、`uuid`、时间、插件版本、命中条款 id、是否在 compact 之后；不存原文。
- 转草稿时 AI 现读本机 jsonl，改写成合成 prompt：保留触发违规的结构，换掉项目名、路径与业务内容。
- 上下文裁到触发轮之前 ≤ 2 轮，作 `context.history_file`；需要的文件用 `context.scaffold_script` 生成合成桩。
- 原文超本机保留期（90 天）已清的候选作废。

**4. compact 之后**：先由 [实测 history_file 回放能否测出「长历史之后」的遵守差](19-probe-history-file-replay.md) 验证。可行则合成回放会话（模板化 compact 摘要 + 1～2 轮尾巴 + 被测 prompt），每个注入插件只挑 ≤ 3 条高风险条款做 compact 版，成本与普通用例相当。离线回放测的是「长历史稀释」：eval 起新会话时 SessionStart 照常注入，测不到注入丢失。「注入在 compact 后是否重新到达」归会话复盘（查 `compact_boundary` 之后有无该插件注入）加静态查 hook matcher。

**5. 基线已满足与诱导用例**：
- 新用例先在「不装」臂跑 3 次，≥ 2/3 通过的标基线已满足（`tags`），只作回归守护：比上一版不退化，不计相对不装的差。
- 要量差时起草诱导用例，手法限任务压力、诱人的捷径、长任务稀释，每条款 ≥ 2 种手法。
- 防过拟合：起草者只看条款意图一句话、不看注入原文；grader 判行为、不判措辞。

**6. 每类几例**：
- 注入 · 纪律：每条可判条款 1 个普通用例；基线已满足的另加 2 个诱导用例。
- skill：每个 skill 应触发 2 例、不应触发 2 例（取相邻 skill 易混场景）；「触发后照做」复用应触发例判。
- agent：每个 agent 该派 1、不该派 1、照定义做事 1。
- 注入 · 文风：可机械判定的规则每条 1 例；易读性与信息不丢共用 2～3 个固定场景（带不装臂）。

**7. 每次跑哪些（与预算对上）**：每次对照只跑本次改动触及条款 / skill / agent 的用例，余下预算（`--max-cost-usd` 取 min(10, 本月余额)）按「最久没跑」轮换其余用例；每例每臂 3 次。改版对照两臂（上一版、当前版），每例约 $0.3～1.9，单次约 5～33 例；需不装臂时三臂每例约 $0.45～2.8。devkit-discipline 约 45 条全量轮一遍约需 2～9 次对照；devkit-tool 15 个 skill 约 60 例同样分多次轮完。

**8. 首批审阅**：草稿按优先级分批，每次待审页 ≤ 10 个，先审 probe 已证明有差与复盘已命中的条款；未审条款在报告里列「无用例」，不算失败。首批约 5 批，按每月 ≤ 1 小时约 1～2 个月审完。

**未选**：以复盘候选为主、只用 AI 起草；作者在注入源码手写条款 id、不立清单；复盘时存脱敏片段、原文进用例；截取真实 compact 片段、真跑到 compact；一律写诱导版、基线已满足的不测；每次全跑每臂 1 次、AI 每次自选 ≤ 10 例；skill / agent 只各 1 正 1 负、只测改过 description 的 skill；首批一次性审完、规则判分草稿免审。

**残余不确定**：
- `history_file` 的格式与回放效果未实测，由 19 回答。
- 条款清单随注入改版怎么同步、条款拆分 / 合并 / 删除时旧 id 与旧用例怎么处置，未定，记入地图「Not yet specified」。
- 「基线已满足」的 2/3 阈值与「最久没跑」轮换的具体记账，属实施细节；轮换可从各 `run.json` 现算，不另存状态。

**重开条件**：
- 19 测不出长历史后的差，按 [缺口里哪些自建、以什么形态](09-build-vs-extend.md) 的重开条件重议第 4 条。
- 首批草稿两个月仍没审完一半，重议第 8 条的分批与优先级。
- 轮换导致某条款连续 3 个月没被跑到，重议第 7 条。
