# hook 克制原则：默认不加 hook，能 100% 机械判定才可以

本仓做插件时，**hook 是最后手段，不是首选手段**。新增任何 `PreToolUse` / `PostToolUse` /
`UserPromptSubmit` / `SessionStart` 拦截类 hook 之前，先过下面的判据表；过不了就不要写。

原因不是"hook 麻烦"，而是拦截类 hook 的失败模式极其昂贵：`permissionDecision: "deny"`
**不给用户"点一下就过"的入口**，AI 撞上去只能猜判据、改写法、反复重试。于是一个判据不准的
hook 制造的典型场景是——**AI 做对了却过不去**，而用户看到的是 AI 在原地打转。

## 判据分级：什么能做成 hook，什么不能

唯一的分界线是**判据是否取自确定信息**。

### 可以做成 hook

判据取自工具输入的**确定字段**或**纯计数**，不需要理解语义：

- 字段是否存在、是否为空（`model` 缺失、`description` 无正文）
- 字段值是否在闭合枚举内（`model` ∈ {`sonnet`, `opus`, `fable`}）
- 字段是否匹配一个**完整锚定**的正则（`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` —— 注意有 `^` 和 `$`）
- 纯计数与阈值比较（文件行数 > 1000、字符串长度 > 60）
- 结构化数据的路径存在性（JSON 里某个 key 有没有）

这类判据的共同点：**同一个输入永远得到同一个结论，且结论可以人工复核**。

### 不能做成 hook

判据需要"猜"，无论正则写得多复杂：

- **需要理解语法上下文**：某个词是真实调用，还是出现在字符串字面量 / 注释 / heredoc / 正则
  字面量内部。整行 `test()` 无法区分。
- **需要理解语义**：这段文字是不是"prompt 原文"、这个任务是不是"核实类"、这个命令是不是
  "写操作"、这条路径是不是"非 ASCII 路径"。
- **需要回读 transcript**：本轮 AI 说过什么、之前有没有声明过什么。历史行的最终排列不等于
  hook 触发那一刻的可读状态（详见下方 §实证 3）。
- **抓的是文本形态而非真实风险**：判据命中的是某种写法长相，而造成风险的是另一件事。这类
  hook 同时误报和漏报（详见 §实证 2）。
- **需要在整条输入里搜某个标记**：搜索范围必须等于约束范围。对整条命令做全局存在性判定，
  标记就会退化成一个口令——写在 `echo` 里、注释里、另一个片段里都算数（详见 §实证 6）。

这类规则**该放哪里**：写进注入文本（`SessionStart` / `UserPromptSubmit` 的 additionalContext）
或 skill 正文，靠 AI 自觉遵守。软约束漏一次的代价，远低于硬拦截误杀一次。

## 强度阶梯：先从最弱的开始，别一步跳到 deny

| 强度 | 手段 | 什么时候用 |
|---|---|---|
| 1（最弱） | 什么都不做 | 违反后果轻微，或本来就是偏好而非规则 |
| 2 | 注入提醒（`additionalContext`） | 判据要猜语义。**大多数规则的正确落点** |
| 3 | `permissionDecision: "ask"` 弹确认框 | 判据能机械判定，但**用户可能有正当理由要放行**（外部写操作、发布、跨组织操作） |
| 4（最强） | `permissionDecision: "deny"` | 判据 100% 确定 **且** 没有任何正当例外。极少数情况 |

从 4 退到 3 通常就能解决"误杀"问题：`ask` 给了用户一个出口，而 `deny` 没有。
参考 `radnove-core` 插件的 `hooks/pre-tool-use-dws-write.sh`——钉钉写操作用的是 `ask`，
不是 `deny`。

## 新增 hook 前必须回答的六个问题

写不出答案就说明还不该做成 hook：

0. **它挂在哪个事件，那个事件到底能不能阻止这次操作？** 先查清楚再写文案。`PreToolUse`
   的 `deny` 能真正拦下调用；`PostToolUse` **不能**——文件已经写完、命令已经跑完，
   `exit 2` 只是把 stderr 喂回给 AI，连本轮都不会停（Claude Code 2.1.220 二进制明文：
   `On PostToolUse, the reason is fed back to Claude and the turn continues.`；真要停住
   回合得输出 JSON 字段 `preventContinuation`）。这一问排在最前面，因为答错它会让后面
   五问的答案全部建立在错误前提上——详见 §实证 5。

1. **判据的确定字段是哪个？** 说出具体字段名与比较方式。答案里出现"匹配……这类词"
   "包含关键字"就说明是在猜语义 → 退回强度 2。
2. **假阳性长什么样？** 构造一个**合法正确**但会被这个判据命中的输入。构造不出来才算通过；
   构造出来了就得先收窄判据。
3. **假阴性长什么样？** 构造一个**真的该拦**但能绕过的输入。绕过方式越简单，这个 hook 越
   接近装饰品。
4. **AI 撞到之后能不能一次改对？** 拦截文案里有没有**可直接照抄的正确写法**？只写"禁止 X"
   会导致反复试错（见 §实证 2 的对照）。
5. **失灵时会怎样？** 判据依赖的外部数据结构（transcript 行格式、payload 字段名）变了之后，
   这个 hook 是静默失效还是永久拒绝？有没有次数熔断？

## 实证（都是本仓真实发生的，不是假设）

### 实证 1：整行正则不解析字符串上下文，产生假阳性

`plugins/portable-shell/hooks/portable-shell-lint.js` 的 `RULES` 数组有 13 条判据，实现方式是
去掉整行注释后对整行做 `test()`。2026-07-31 实测：

```sh
echo "grep -P test in a string..."     # 只是输出一段说明文字
```

这一行被 `grep-P` 规则命中并报为不可移植调用。它**根本没有调用** `grep -P`。同一次实测里
真实调用（`grep -P 'foo' realfile.txt`）也被命中——也就是说这条判据无法区分两者。

该缺陷已如实记录在 `plugins/portable-shell/hooks/portable-shell-lint.js` 的文件头注释里。
注意这个 hook 走的是 `process.exit(2)`（把 stderr 喂回给 AI 的一次性提醒，文件已写入、
不回滚），**不是** `deny`——所以假阳性的代价只是一条噪音。若同样的判据被做成 `deny`，
每次写这种说明性 `echo` 都会被硬拦。

### 实证 2：判据抓形态不抓风险，同时误报和漏报

`plugins/working-discipline/hooks/guards/bash-guard.js` 禁止"污染 cwd 的独立 `cd`"。
2026-07-31 同一会话内的两次真实调用：

```sh
cd /abs/path && wc -l file        # 被拦
(cd /abs/path && wc -l file)      # 放行
```

子 shell 写法**同样改变了该命令内部的工作目录**，只是变更不泄漏到父 shell。所以判据实际
命中的是"`cd` 是否以独立命令形态出现"这个长相，而不是"cwd 是否被污染"这个风险。

同日一次专项审计跑了 **103 条真实 payload**，把上面这句从推测变成了实测清单。真污染却
放行的有 19 类：`pushd` / `source` 或 `.` 引入含 cd 的脚本 / `eval 'cd ...'` / `\cd` /
`builtin cd` / `command cd` / `"cd" /tmp` / `CDPATH=/ cd tmp` / `time cd` /
`git status & cd /tmp`（单个 `&` 在切分器里没有语义）/ `if...then cd` / `{ cd; }` /
`for...do cd` / `case...) cd` / 函数体内的 cd。

更能说明"抓形态"的是这组对照——`lib/shell-parse.js` 的 `stripSubshells` 用
`\([^()]*\)` 剥子 shell，**这个正则不感知引号**：

```sh
echo "(start" && cd /tmp && echo "end)"    # PASS：假括号配对，真 cd 被整段吃掉
echo "a)" && cd /tmp                       # BLOCK：只有 ) 没有 (，剥不掉
```

这也顺带解释了 `(cd /abs && cmd)` 为什么放行：**不是因为判定了"变更不泄漏到父 shell"，
而是因为括号里的文本被删掉了**。旁证是 `(cd /tmp && ls) && cd /var` 仍然被拦。判定同一
个事实的两条命令，结果由括号字符的位置决定，不由 cwd 是否被污染决定。

误报方向同样实测到四类，最严重的是 **heredoc 正文**：切分器把换行当命令分隔符，于是
`ssh prod bash -s <<'EOF' / cd /srv/app / ... / EOF` 被判本地污染，而那个 `cd` 在远程
主机执行；`python3 - <<'EOF'` 正文里的 `cd` 甚至根本不是 shell 命令。更糟的是 hint 给
的两个模板（改绝对路径 / 套子 shell）对 heredoc 正文**无从下手**——正文是给远端读的文本，
套上括号只会把括号写进远端脚本。这四类误报已在 3.6.0 修掉（新增 `stripHeredocs`、
no-op 判定加 `realpath` 与 `$PWD`、后台化片段放行），19 类漏报按用户拍板**不补**——
补一条就多一个误杀面，且永远补不全 shell 语法。现状如实写进了该文件的文件头。

同一条规则还提供了一个**正向对照**，说明拦截文案给模板有多重要：该 hook 的 finding 文案里
直接给了 `(cd /abs && cmd)` / `git -C <path> <cmd>` 两个可照抄的模板，撞到的 AI **一次就
改对了**；而同一条规则以软文本形式注入时，同一个 AI 读过却照样违反。判据准 + 文案给模板 =
一次改对；这是 hook 值得存在的样子。

**但要注意这个"改对"是什么意思**：AI 照模板把命令改成 `(cd /abs && cmd)` 之后，它只是
让文本形态躲开了正则，cwd 是否真的干净并没有被验证。判据抓形态时，"过闸"和"合规"是两件事。

### 实证 3：靠回读 transcript 判定，会永久拒绝

`working-discipline` 曾有 `md-audience-declaration.js`，判据是回读 transcript 找本轮 AI 有没有
说过「受众判定」。它在 2.3.0 被摘除，根因是两条错误结论叠加成死局：

一是轮起点算法「从后往前找最后一个 `promptId` 匹配的 user 行」必然命中**最近一次工具结果**
（`tool_result` 行的 `type` 也是 `'user'` 且带同一个 `promptId`），起点被推到它之后，AI 之前
说过的话全被切掉。二是一条 assistant message（thinking + text + tool_use）要等 API 响应
结束才整体写盘，而 `PreToolUse` 发生在那之前——**同一条 message 里的 text 块，在该 message
的 tool_use 触发 hook 时读不到**。前者决定"重试时旧声明又被新 tool_result 挤出窗口"，后者
决定"首次必然读不到"，合起来就是每次重新声明都会再造一个 `tool_result` 把声明推走。

事故现场的 AI 在两次被 deny 后判断"这是个失灵的时机检查"，转而用 heredoc 绕开 `Write` 工具
直接写文件——**判据不可靠的硬拦截，最终教会 AI 绕路**。

这次留下的教训是：给依赖外部数据结构的门控 hook 补上可观测性（判据写进 deny 文案 + 次数
熔断）只能让失灵可诊断，**不能让不可靠的判据变可靠**。真正的结论是这类判据压根不该做成拦截。

### 实证 4：3.0.0 一次性删掉四个关键词判定的 guard

`working-discipline` 在 3.0.0 删除了 `external-write-readback.js`（扫命令里的
create/update/delete/发布 等词）、`nonascii-path.js`（把命令行里任何非 ASCII 字节都当成
"路径含非 ASCII"，连 `echo '=== 已安装缓存版本 ==='` 的中文提示语都算）、
`md-audience-declaration.js`，以及 `agent-dispatch.js` 里的四条第二层检查。

共同缺陷是判据靠正则猜语义，而 deny 是不可绕过的硬阻断。对应的纪律**一条都没丢**，全部
回到注入文本里靠自觉——遵从度略降，换掉了"做对了却过不去"这个失败模式。

### 实证 5：hook 的实际效力与文案会各自漂移，没有任何环节自动核对

`plugins/working-discipline/hooks/guards/write-guard.js` 挂 `PostToolUse(Write|Edit)`，
检查源码文件 >1000 行与 `CLAUDE.md` >200 行。同插件注入给 AI 的纪律第六章写的是这两条
**「会被拦」**。2026-07-31 审计用三条独立证据证明它拦不住任何东西：

一是它全文只有两处 `readFileSync`（读 stdin、读目标文件），没有任何 `fs` 写操作，不做也
无法做回滚；审计连续 6 次拦同一个 12436 行文件后复核 md5 与 mtime 逐字节未变。二是它读到
的行数就是**写入后**的行数——finding 里那个数字本身即证据。三是 `PostToolUse` 的语义在
Claude Code 2.1.220 二进制里有明文（见上面第 0 问），而它走 `exit 2` 不输出 JSON。

后果不是"少拦了一次"，而是**主代理在错误前提下工作了整整一轮**：它读到"会被拦"，据此
认为超长文件有机械兜底，把注意力分配给了别处。

这里的通用教训比 `write-guard` 本身重要：hook 的**实际效力**（由挂载事件和输出形式决定）
与描述它的**三处文案**（源码文件头、注入文本、README）分别演进，谁都不会自动去核对另一方。
本例里三处全错且方向一致——都把它说得比实际更强。所以：

- 写文案时用**动作**描述而非**结果**描述。"文件超过 1000 行会给出提示"是可核验的；
  "会被拦"混淆了 `PreToolUse` 的 deny 与 `PostToolUse` 的 stderr 回灌。
- 同一个 hook 的效力描述出现在几个地方，改判据时**逐处同步**，别只改代码。
- 源码文件头里的自我评价（"精确"、"误判空间为零"）是最容易过期的一类文字。同一次审计里
  `write-guard.js` 的"误判空间为零"被三类误判证伪（扩展名不能区分源码与数据/产物/依赖、
  行数计数带 +1 偏移、basename 不能区分本项目与第三方），`bash-guard.js` 的"精确定位"
  被上面实证 2 那 19 类漏报证伪。**写这类断言前先跑 payload，或者干脆别写断言，改写
  覆盖边界清单。**

### 实证 6：全局字符串存在性判定会退化成"口令"

同一份 `bash-guard.js` 要求 `agent-browser` 的启动类子命令必须带 `--headed` 与
`--profile`。原实现对**整条命令字符串**扫一次这两个标记，各命令片段共用结果。实测：

```sh
agent-browser open https://x --profile /tmp/p && echo "--headed"   # PASS
echo --headed; agent-browser open https://x --profile /tmp/p       # PASS
agent-browser open https://y --profile /p --json "{--headed}"      # PASS
```

约束退化成了一个**口令**：写在 `echo` 里、注释里、JSON 参数里都算数。这类 hook 对"偶然
遗漏"有效，对"想绕过"零成本——而它却是硬阻断，误杀的代价由不想绕过的人承担
（`agent-browser open --help` 被判缺两个参数，查帮助不会拉起任何浏览器实例）。

判据设计的取向由此明确：**存在性判定必须绑定到它要约束的那次调用的作用域内**，不能对
整条输入做全局搜索。3.6.0 已把判定收窄到单次调用的参数列表与紧邻的环境变量前缀。

## 已存在的 hook 怎么办

不要因为这条规则去批量删除现有 hook。处置顺序是：

1. **先测**：构造假阳性与假阴性输入，实际跑一遍（`echo '<payload>' | node <hook>`），
   拿到真实输出，不要靠读代码推断。
2. **能收窄就收窄**：判据能改成锚定正则或确定字段的，改。
3. **收窄不了就降强度**：`deny` → `ask` → 注入提醒。
4. **改判据必须用户拍板**：判据影响硬阻断行为，AI 不得自行修改判据、正则、阈值、
   `permissionDecision`。发现问题**只报不改**，把可复现的输入与实际输出交给用户。
   区分两类：判据松紧要拍板；实现 bug（哈希输入漏字段、行数差一、剥引号漏一层）
   不改变判定意图，可以直接修，但要在回执里单独列出来。
5. **改完留回归用例**：一次性跑过不算数——判据两侧都要有用例（旧版误杀现在应放行的、
   旧版正确拦截现在仍应拦截的），用 `spawnSync` 喂 JSON 到 stdin，**不经过 shell**。
   经过 shell 的测试脚本一旦引号失衡，guard 会把你的测试数据当成真命令拦下并原样回灌
   进 finding——2026-07-31 审计真撞了一次，单条 finding 被撑到 900+ 字符。

## 这条规则自己的适用边界

它约束的是**拦截类** hook（`PreToolUse` / `PostToolUse` 的 deny·ask·exit 2）。以下不受
本规则限制，不要"顺手也删掉"：

- **纯注入类 hook**（`SessionStart` / `UserPromptSubmit` / `SubagentStart` 只输出
  `additionalContext`）：它不阻止任何操作，失败模式只是"多占了上下文预算"，判据是不是
  近似无关紧要。本仓 `working-discipline` 的三层注入就属于这类。
- **`permissionDecision: "ask"`**：它把决定权交回给用户，判据宽一点的代价是多弹一次
  确认框，而不是"做对了却过不去"。判据只有七八成把握时，`ask` 是比不做更好的选择。
- **既有 hook 的实现 bug 修复**：见上一节第 4 条的区分。
