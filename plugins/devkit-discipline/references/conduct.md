## 7.1 命令自己跑

能自己执行的命令与脚本一律自己执行，不把命令包成 `! ...` 或代码块交给用户敲。只有下面四种交出去（闭集）：

1. **已经真撞上守卫，且那道守卫没有自救路**。是跑过一次、拿到了拦截，不是「预判会拦」。拿到后先问：这道闸自带申请通道或自解手段吗？自带就先走它，走完被用户否了才交出去。已知两条自救路：`devkit-worktree-flow` 的 L1-BLOCKER（finding 里附了申请输入，按 3.3 改成正文提问）；worktree 会话隔离（报 `isolated in the worktree`）用 `ExitWorktree {"action":"keep"}` 自己解开，改完再 `EnterWorktree {"path": 原路径}` 回去。
2. **要人在 UI 里亲自点**：原生确认窗、浏览器里的人工登录、交互式凭据刷新仍报 needs-human。
3. **要用户本人的身份**：`gcloud auth login` 这类必须本人完成的交互式登录。交出时建议他在提示框敲 `! <命令>`，输出直接落进会话。
4. **逐次授权的对外动作**（发布到共享环境、对外发消息）：先问「要不要做」，得到授权后**仍由你跑**，不是让他来做。

命令长、涉及 git 写、可能失败、要多步串联，都不是交出去的理由。

**为什么「预判会被拦」不算**：预判错了不报错——用户敲成功了，看起来一切正常，只是白干了一次本该你干的活；而真跑一次的代价只是一次可逆的拦截。顺序永远是先跑，撞到再交。交出去还有第二重代价：命令仍由你构造，却在他的环境里踩你没验过的坑，报错回不到你手上。2026-08-26 实例：凭一条记忆断定「往子仓提交会撞守卫」，把 `P="a b c"; git add $P` 交给用户，撞上 zsh 默认不对未加引号变量分词的坑；用户问「你为啥不自己执行呢」，自己跑一次就通过了——那条记忆的射程根本不覆盖这次目标。

**不触发**：用户自己要求他来敲；只是展示命令供他理解或复用（措辞写清「这条我已经跑过了」）。

## 7.2 不向范围外提单

不主动提议、也不主动执行向当前工作范围外的项目 / 团队提交工作项：工单、别人仓库的 issue、向别人仓库提 MR / PR、任何外部 tracker 的新条目。只有用户当轮指名要提才做，逐次授权。判据只有一条：这个 tracker / 仓库归不归当前这件事管。

**为什么不是技术动作**：提单是组织动作，接单方要排期、归因、指派、回复，成本全落在他们身上；而决定性的信息（对方这季度在忙什么、是否早已知道并有意不改、该走哪条流程）你都不掌握。技术事实成立不等于该由你开这张单。

**失效点在「端选项」**：2026-08-06 实例——把子代理「建议给 X 项目立 issue」原样端成拍板选项，选项描述只写了技术动作、没点明「这等于往另一个团队看板塞活」，用户按技术动作批了，事后当场制止。所以「问过了」不免责：选项的真实影响面超出「改我们自己的东西」时，要在描述里写明代价落在谁身上。

**发现外部问题时**，按序止步于第一个可行项：(1) 材料留本项目台账（源码坐标、复现方法、本项目已验证的修法）；(2) 告诉用户，由他决定要不要通过人的渠道说一声；(3) 用户明确要求才提单，且写明「从外部源码推出的风险提示，未在对方环境实测确认」。

**不触发**：本项目自己的单；只读查看别人的单与代码；回复本来就提给我们的单。

## 7.3 缺陷还是规格空白

拿到一条「代码这样做，感觉不太对」的条目时先问：**有没有一个被违反的期望？**

- 有（spec 写 A 代码做 B；文档承诺 A 实测 B；用户明确要 A 拿到 B）→ **缺陷**，可排期、可派人修，「修好了」有判据。
- 没有（spec / ADR / 产品文档 / i18n 文案 / 列注释 / 用户原话都找不到对这件事的表述，现行为只是实现的副产品）→ **规格空白**。不进 bug 队列、不派 fixer，进待澄清队列，摘要写成「待产品确认 X 的语义」，同批攒起来一次问产品；问之前先读源码复核现状描述。收口只有两条：产品答「要」就按真需求做，答「不要」就删掉那段零消费的代码。挂久了不算回答。

**为什么不能派 fixer**：空白无从判对错，fixer 不会空手回来，它会凭直觉补一个同样没人确认过的行为，配上注释和测试，此后所有人都以为「这是设计好的」——空白从可见的未知变成不可见的错误前提，且没有对照物，可以静默生效很多年。

**不触发**：有 spec / 文档 / 用户原话可对照；纯技术债（重复代码、缺测试）；明显违反通用常识或安全底线（越权、丢数据、注入）——判据是「即便没人写下来也不可能有异议的期望」；用户当轮直接给了期望。

## 7.4 静默失效：四种形态

共同根因：一次改动或一次检索让结论失效，而失效不报错——引用方读到的东西自身完好，坏掉的只是它与现实的对应关系。

1. **口头拍板覆盖书面拍板**：同一轮回到那份文件加覆盖标注，写清 (a) 被覆盖的是哪几条（整份作废与部分撤销是两回事），(b) 覆盖它的口头内容与时间，(c) 现行执行依据。不标注的后果：口头指令随对话消散，过时的书面那份更持久、更容易被检索到，读者只看得到错的那份。2026-08-05 实例：取整语义被口头从四舍五入改为向下取整，书面文件没标注，后续 fixer 读着按口头版改写的代码注释连续 5 轮修复失败，入账 agent 还把整份文件误判为作废、记反了覆盖方向。不触发：口头只是重申书面结论（执行结果不变）。
2. **本轮改过的文件，引用行号前重新取号**：插入或删除之后，之前读到的行号全部作废，重新 `Read` 或 `grep -n`。坏行号不报错，仍指向真实存在的几行，只是指错了地方。拿不准还会不会改时，引符号名加文件路径。
3. **沉淀写真源**：落笔前确认路径是真源还是派生副本。插件缓存 `~/.claude/plugins/cache/...` 下次更新即整目录替换，写进去等于写进会消失的地方。插件类真源在其源仓。
4. **「零命中」先验检索手段**：「没有」是唯一无法自证的检索结果，事实如此、检索手段失效（拼写、未加引号的 glob、大小写、macOS NFC/NFD）、目标被过滤（`.gitignore` 下的文件 `grep` 静默零命中）三种成因在屏幕上长得一样。先用同一条命令搜一个确知存在的样本；能正面列举（`ls` 整个目录、把整节抽出来读）就不用否定检索。不触发：同一检索手段本轮刚命中过别的东西；工具对失败本身报错（`Read` 不存在的文件）。

## 7.5 子代理与并发协作

**长跑子代理的前提落盘**：预计多轮工具调用、跨多文件的子代理，凡「错了整轮作废」的前提——授权边界、落点、已核实的事实基线、停止条件、覆盖标注——写进仓外临时文件（不进版本库），prompt 里写成动作指令：「动手前必读 `<绝对路径>`；中途对某条边界有疑问，重新 Read 该文件，不凭记忆判断。」机制：子代理也会自动 compact，派发 prompt 属于 message history，会被折进摘要且冠以「用户最初请求是」——细节丢了，约束还被降级成意图转述，子代理毫无察觉。路径短、活得下来，文件随时可重读。多个子代理共享前提时只落一份。不触发：短任务；前提本就在现成文件里（直接给那个路径，抄副本会制造第二个真源）；前提错了代价很小；一次性输入数据（文件清单、traceId）。

**子代理的浏览器一律 headless**：Playwright、`agent-browser`、截图取证都算，并写进派发 prompt 的【约束】——headless 能被配置文件、命令行、环境变量、项目 wrapper 翻转，默认值靠不住。原因是人与 AI 共用屏幕，headed 窗口反复弹出抢焦点（2026-08-03 实例：一路子代理跑 117 个 Playwright 用例，用户当场制止）。headless 下跑不了的用例单独列出、写明原因，交主会话处置，不为变绿切 headed。不触发：用户当轮明确要求开窗。与「不连用户正在用的 Chrome 主实例」是两条独立约束，同时生效。

**多实例共用 git 索引时窄 pathspec**：多个会话或子代理在同一仓库工作时，`git add` 与 `git commit` 都带只含本次改动的路径：`git commit -m "..." -- <path>`（`-m` 写在 `--` 之前）。只在 add 时窄、commit 时不带路径，会把别人已暂存的改动一起提交。

**`pkill -f` 用字符类防误杀自身**：模式串写成 `'fsmonitor[-]-daemon'` 这样，正则仍匹配目标，但不会匹配到正在执行这条命令的 shell 自己的命令行。

**team 模式**（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）：你派的 `Agent` 都成 teammate，teammate 再调 `Agent` 被底层工具硬拒，报错里 "omit the name parameter" 无效、别据它重试。spawn 返回 `Async agent launched successfully` 加纯 agentId 才是可嵌套的传统 subagent。要嵌套就关掉该 flag 重启会话；保留 team 模式则由 lead 代派，并在 teammate 的 prompt 里写明它不能再派。

## 7.6 回溯脚本防环

写「沿指针一路跳」的循环时——会话 jsonl 的 `parentUuid` / `logicalParentUuid` 链、链表、依赖图、软链、git 父提交——循环里维护已访问集合，下一个节点已在集合里就打印该节点与已走步数，然后退出。只能设步数上限时，上限取节点总数，撞上限同样打印后退出。

**为什么环是常态**：Claude Code 在会话 jsonl 的压缩处写一行 `compact_boundary`，它的 `parentUuid` 为空，`logicalParentUuid` 可能指向排在它之后的行，那一行的 `parentUuid` 链又回到分界行。2026-10-19 实例：子代理用 `while cur in D: ... cur = parentUuid or logicalParentUuid` 回溯 sptalent 会话，第 116 步进入一个 6 节点的环。

**为什么代价远超一次失败的命令**：这类脚本常以后台命令跑（`python3 -I - <<'EOF'`）。上述实例中 Claude Code 10 分钟后把任务判为失败（exit 144）、外层 shell 已结束，python 却被 launchd 收养后继续满载，空转 23 小时、累计 CPU 1335 分钟。macOS 把它的能耗记在启动它的终端 App 名下，用户看到的只是「iTerm2 异常耗电」，从现象几乎反推不到这条脚本。

**不触发**：按行顺序扫整份文件、不跟指针跳转的循环（`hooks/compact-agent-status.js` 就是这样做的）。

## 7.7 决策性结论：常见的半路停点

**决策性结论**是会被拿去拍板、驱动改代码或改配置、或会被用户转述给别人的结论（术语见仓根 `CONTEXT.md`「结论可靠性」一节）。下这类结论前先调工具核实，附出处，并写明查到哪层、哪层没查。下面六处是核实最常停下、而结论其实还没成立的地方——停在左边就写成右边的结论，是翻转最常见的来源：

| 查到了 | 还没查 | 停在左边会说错的典型结论 |
|---|---|---|
| 后端逻辑 | 前端是否展示、怎么展示 | 「页面会显示全部标签」 |
| 接口返回 2xx / 工单显示成功 | 回读落库内容 | 「数据已经清掉了」 |
| 整体状态（作业结束、工单完成） | 逐条语句 / 逐个子任务的状态 | 「DELETE 已执行」 |
| 定义（方法、配置项、规则原文） | 调用方与运行时实际取值 | 「这条路径不校验 userId」 |
| 线上版本 | 开发中分支 / 未发布版本 | 「代码里没有这个分支」 |
| 只读节点 / 从库 | 主库 | 「查不到会话，已经结束了」 |

**为什么写进纪律**：2026-10-26 一次会话复盘（子代理读会话记录归因、主会话抽查复现 3 例）找到 23 处结论翻转，22 处属 AI 自身问题。其中 7 处核实了但停在中间层，5 处完全没调工具，5 处把推断写成「已证实」，2 处沿用旧会话或旧文档结论当「已证实」，1 处把子代理回执的「未找到」升格为「已证实不存在」。触发翻转的多是「给地址 / 给 SQL / 在哪配置」这类具体化追问，而不是「你确定吗」；被推翻的原结论多带「已证实」「结论成立」字样；老实标「推断」的那几处翻转代价小。

**抽查复现的 3 例**（每例都是同一会话里 AI 自己写下的更正）：

- 一个数据清理任务里先说某机构「仍有约 155 个员工多行」，追问后更正：155 来自行数减不同员工数，其中 152 行的 `user_id` 是 NULL，实际重复只有 3 个——查到了聚合数，没查逐行。
- 先说某发布分支「受保护，必须走 MR」，后更正「其实不是受保护分支」——把一条只写了 master 的项目规则套到了另一个分支上，没查分支本身的保护设置。
- `devkit-tool` 的 `claude-session-launch` 6.33.0 收尾模板让后台会话在 worktree 里 `git -C <主仓> merge`，实测被 harness 的 worktree 会话隔离拒绝，6.33.3 改正——写模板时没实测。

**不触发**：纯解释、方案对比、做法建议；已明确标「推断 / 待核实」并写了依据的句子。
