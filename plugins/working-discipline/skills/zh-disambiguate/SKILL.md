# 中文消歧审计

目标：让每个关键句的执行者、对象、作用范围、动作状态和确定程度都能从字面读出。这不是把中文写得像简化英语，也不是追求句子变短——为凑短而删掉对象、条件、判定标准，是本 skill 要抓的错误，不是要做的事。

判据细则（四类歧义、三类内容各自怎么控、改写的原意检查）在 [references/rules.md](references/rules.md)。第 3 步开始前读完它。

## 步骤

### 1. 定输入与模式

- 输入：用户给的文件路径、粘贴的段落，或调用方（如 spec-analyze）指定的文件。
- 模式：默认**审计**。用户本轮明确说「改」「改写」「直接改掉」才进**改写**模式。
- 找概念表：从输入文件所在目录向上找到仓库根，读根目录的 `CONTEXT.md`；没有就记「无概念表」，术语层只查文内一致。

完成判据：输入范围、模式、概念表有无，三项都已确定。

### 2. 形式层：跑脚本

```bash
node <本 skill 目录>/scripts/scan.js <文件路径>...
# 粘贴的文本：先写进系统临时目录的文件，再传路径
```

脚本只预警，不判定合规。它报三类：句长超过 60 字、一句里出现两个及以上「并 / 再 / 然后 / 同时 / 接着 / 随后」、句首用「该 / 此 / 上述 / 这个 / 那个」指代。每条预警都要在第 3 步人工判定：很多长句因为写全了对象和判定标准而更清楚，它们应判为「无问题」。

完成判据：脚本输出的每一条都进入第 3 步的判定。

### 3. 术语层与语义层：逐句判定

先给全文按内容类型分段（操作步骤 / 原理解释 / 排障判断），类型决定该段重点查什么，见 reference 的「三类内容」。

然后逐句过一遍。**关键句**指含动作、权限、条件、状态变化或结论的句子；关键句每一句都要查完下面五项，非关键句只看脚本预警：

1. 执行者：每个动作是谁做的？上下文出现两个及以上可能执行者时，句中必须写明。
2. 指代：「该 / 此 / 它 / 上述」指的是哪个对象？能否唯一确定？
3. 作用范围：量词、否定、「或 / 和」、条件各管到哪些对象？
4. 动作状态：这句是指令、已完成、进行中，还是条件触发？
5. 术语：同一概念是否换了叫法？不同概念是否用了同一个词？与概念表冲突吗？

完成判据：每个关键句五项都已判定，每条脚本预警都已判为「有问题」或「无问题」。

### 4. 输出

**审计模式**输出一张表，只列有问题的句子：

| 位置 | 原句 | 歧义类型 | 需要澄清什么 | 按不同原意的写法 |
|---|---|---|---|---|

- 位置写 `文件:行号`；粘贴文本写段号。
- 「按不同原意的写法」列出每种可能原意各自怎么写。原意只有作者知道，审计不替作者选。
- 表后一句话给统计：关键句几句、有问题几句、脚本预警几条、其中判为无问题几条。

**改写模式**在审计表之后给改写稿，再给原意检查表（格式与判据见 reference 的「原意检查」）。原文没写明的执行者、范围、条件，在改写稿里标「待确认」，不补造。

完成判据：审计模式下表格与统计都已给出；改写模式下改写稿与原意检查表都已给出，且原意检查表逐条对应每一处改动。

## 被 spec-analyze 调用时

审计对象是即将落盘的 `spec.md`。把审计表交回 spec-analyze：能从需求澄清记录里确定原意的问题，由 spec-analyze 直接改；确定不了的，在 spec.md 对应位置标「待确认」并列入向用户的提问。本 skill 在这条路径上不进入改写模式。
