# 复杂度优先（Complexity First）

新增功能、新文件、新脚本、新依赖之前，先证明"确实需要新增"，再按固定顺序穷尽复用路径，只在全都不成立时写最小新增实现。核心产出是一份决策记录：比较过哪些方案、为什么选这个、放弃了什么——让"这段新代码为什么存在"有据可查，而不是凭直觉落笔。

## 适用范围

本 skill 覆盖一切"新增"：新功能、新函数、新脚本、新配置项、新依赖、新文档段落。它管"要不要新增"和"以最小面新增"两件事。

以下场景不套本流程，直接按既有工作流走：

- 修 bug、改既有实现、纯重构——仅改既有代码且不引入新函数、新文件、新配置或新依赖。
- 架构方案已经拍板、正在按方案实施——方案比较在那之前已完成。
- 用户明确指定了实现路径——他的话就是结论，照做。

修复或重构若需要新增实现，仍先执行第 1 至第 5 步：确认是否真需新增，再搜索可复用能力；只有找不到合用路径时才进入第 6 步。

## 决策顺序：六步，命中即停

每一步都有明确的命中判据。命中 = 该路径已有可用物，停下来用它，不再往下走；六步全不命中才新增。顺序不能跳：先近后远、先具体后通用、先零成本后有成本。跳步要有理由，写进决策记录。

### 第 1 步 必要性：需求能否不新增就达成

先问"这件事是否需要任何新代码"。需求的目标能否用既有行为组合达成——改个配置、调个参数、换种调用方式、改一段既有代码？

- 命中：不写任何新代码也能达成，记录"为什么不需要新增"。
- 未命中判据：确认目标行为在现状下确实不可达（缺功能、缺入口、缺数据）。
- 完成标准：能说清"需求的目标是什么、现状缺了什么"，而不只是"需求说要做"。

### 第 2 步 现有代码、抽象与配置

在当前仓库搜索已有实现或半成品：同功能函数、可复用抽象（类/组件/工具层）、配置开关、环境变量、既有脚本。仓库内已有的东西零成本，且已被本仓库的测试与部署验证过，优先于一切外部资源。

- 命中：已有实现直接复用；已有半成品（接近但差一点）优先扩展它，不另起炉灶。
- 未命中判据：用关键词搜过代码与配置（含文档/注释里描述的未实现意图），确认仓库内无可用物。
- 完成标准：能列出"搜了什么关键词、查了哪些目录、为什么判定没有"。

### 第 3 步 标准库

当前语言自带的标准库能力。标准库零依赖、随语言版本维护、全团队共享，永远先于第三方依赖。

- 命中：用标准库实现，不引入任何新依赖。
- 未命中判据：查过当前语言版本的标准库文档/索引，确认目标能力不在其中。
- 完成标准：能说出"查过哪份标准库依据、缺的是什么"。

### 第 4 步 平台原生能力

宿主平台（操作系统、运行框架、运行时、云平台）自带的能力：系统命令、框架内置模块、平台 API、平台内置存储/队列/调度等。

- 命中：用平台能力实现，优先于新增依赖。
- 未命中判据：确认平台没有内置该能力，或内置能力不满足必要约束（如权限模型不符）。
- 完成标准：能说清"平台原生方案查过哪个、因哪条约束不成立"。

### 第 5 步 已有依赖

仓库已安装、项目已在用的依赖里，是否有覆盖该能力的模块——即使它当初不是为这个场景装的。已有依赖的新用途零安装成本，但要留意它是否带进新的权限面或运行开销。

- 命中：用已有依赖的既有 API，不新增安装。
- 未命中判据：查过项目依赖清单（package.json / requirements.txt / go.mod 等）与已用模块的文档。
- 完成标准：能列出"查过哪些依赖、为何判定不可用"。

### 第 6 步 最小新增实现

以上五步全不命中，才写新代码。此时"最小"不是省字符，而是：

- 只实现需求要求的行为，不顺手实现未要求的能力。
- 新增依赖前先权衡：这个依赖替我们省下的工作量，是否大于它带来的安装、维护与权限成本？能不引依赖就不引。
- 新增的文件/函数/配置只承担一个职责，可被单独验证。

## 每轮必须保留的边界

"最小"不等于"砍边界"。以下五类约束在每一次建议里都必须保留；与"尽量少写"冲突时边界优先，冲突本身写进决策记录：

- 安全：不引入新的攻击面；新代码不绕过既有的鉴权与校验链路。
- 权限：操作范围最小化；新能力不自动获得超出其用途的权限。
- 错误处理：新增路径有失败分支的处置，失败可被诊断。
- 数据完整性：不破坏既有数据的读取与写入约定；新写入可回滚或可校验。
- 无障碍：面向用户的界面与文案不因新增而失去可访问性。

## 规格空白：要求澄清，不替用户定义

需求里若存在"正确行为没有人定义过"的部分——没有 spec、没有文档、没有用户原话定义它的语义——不要猜一个行为补上。猜测会把一个可见的空白变成一层看起来深思熟虑的实现，此后任何人读它都会当成设计好的。

动作：把空白点列出来问用户"这里期望的行为是什么"。用户给了定义，按定义实现并记录；用户确认这是空白，连同你的建议方案一并交给他拍板。

## 输出：决策记录

每次建议（无论是"用已有物"还是"写新代码"）都以一份决策记录收尾，五项缺一不可：

1. **方案比较**：至少两个候选路径及各自的代价（新代码量、依赖、风险）。
2. **选择**：选中哪个，对应上面第几步的命中。
3. **放弃理由**：被放弃方案各一句理由，含"为什么不到更远的一步去取"。
4. **不可删边界**：本轮保留的安全/权限/错误处理/数据完整性/无障碍边界清单。
5. **验证**：怎么证明选择成立——命中已有物时指出现有测试或复现路径；新增实现时给出可执行的最小验证。

示例（新增一个临时文件清理脚本的场景）：

```markdown
1. 方案比较：a) 写一个独立清理脚本；b) 复用项目既有 tmp 清理任务（只差目录参数）
2. 选择：b，第 2 步命中——仓库已有同职责脚本
3. 放弃理由：a 弃——会造成两份维护同一逻辑；标准库/依赖路径未到，因第 2 步已命中
4. 不可删边界：目录参数白名单校验、删除前 dry-run、错误日志（安全/错误处理）
5. 验证：对一条既有已过期临时目录跑 dry-run，对比清理前后目录列表
```

## 自查：本 skill 执行到位

- 决策顺序第 1→6 步没有跳过（跳步有理由）。
- 决策记录的"放弃理由"每条都写得清——写不清说明那一步没查透。
- 五类边界逐条过了一遍，没有被"最小"顶掉。
- 规格空白交给了用户，而不是被自己补上。
