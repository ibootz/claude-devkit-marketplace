# collector：动手前把规格收齐（prompt 模板）

派给 `general-purpose` 的**第 2 层**子代理，形态与 fixer / review 完全同构：只有一份
prompt 模板，没有 agent 定义、没有队列、不落盘任何独立产物。它的输出直接回到派它的
keeper 手里，由 keeper 决定怎么用。

## 何时派

修一条 bug 之前，出现下面任一情形就值得先派一个 collector：

- **改动会碰到「按规格该怎样」这个问题**——文案、校验规则、字段语义、错误码、边界值。
  这类地方凭直觉改，改完看起来对，但很可能违反某处写着的约定。
- **同一形状的东西可能不止一处**——同一个错误码、同一段校验、同一句文案是否在别处
  也复制了一份。只修看得见的那一处，等于把同一个 bug 留在别的入口。
- **triage 时答不出「正确行为是什么」**——先收集，收集完仍答不出，那是规格空白不是
  缺陷，按 `.claude/rules/` 的 `defect-vs-spec-gap` 转 chore 队列问产品，不要派 fixer。

## 什么时候不派

- **现象与规格无关**：崩溃、空指针、超时、内存泄漏这类纯实现缺陷，正确行为无需查证。
- **一眼定位、改动落在单个函数内**——收集的成本高于修复本身。
- **用户当轮已经把期望说清楚了**——他的原话就是权威规格，直接用。

## 模板（`<>` 里的占位符派发前必须全部替换掉）

```
你是被派发的第 2 层子代理，只读收集，禁止修改任何文件，禁止再派任何 subagent。

【目标】
在动手实现 <功能单元名 / DBG-NNN> 之前（或在派 fixer 之前），把管辖它的规格与约束找全，
标出信源之间打架或空白的地方，产出一份实现者可以对照执行、后续能核实是否做到的断言清单。
你只收集与汇报，不判断怎么实现、不写代码、不建议修法。

【上下文】
仓库根绝对路径：<仓库根绝对路径>
功能单元边界（一句话说清"必须一起验证的那组断言是什么"，例如"31 条导入错误提示文案"
而不是"导入模块"）：<要收集的功能单元边界>
用户原话（逐字，不转述）：<用户原话>
截图（如有，给绝对路径，你自己 Read）：<截图路径，无则填"无">
已知锚点（需求文档路径 / DBG 编号 / 领域词典条目名 / spec 目录约定，没有就留空，你自己找）：<已知锚点>
场景：<implement：首次实现，不必做第 5 条同构检索 | debug：修复缺陷，第 5 条同构检索必须做>

【约束】
逐一检索下面几类信源，每一类都要给出结果（命中 / 未命中 / 本项目不存在这类信源），
不要只查一类就下结论，也不要因为某一类"看起来更权威"就把它当唯一入口去展开：

1. 需求侧：需求文档、产品文案、用户原话。如果是表格或编号清单，必须按行展开成一条条
   断言，不许压成一句"按文档表格实现"——已实测的事故是报告只提一条，其余全部静默漏做。
2. 原型（如有 `*.prototype.html` / `*.proposal.html` / demo）：**原型画出来不等于
   文字规格也这么写**，两者分开记录；只查了原型就下"规格已确认"是不合格的收集。
3. 文字规格（如有 spec / contracts / entities / gherkin / view spec 等文档）：
   追到本单元对应的文档边界为止，不必扫整个仓库。
4. 领域词典 / ontology（如项目有）：先读索引文件定位到具体条目再读，不要整目录扫描；
   条目若标了"未经人确认"或置信度低，要注明，并回溯它引用的原始规格核实一遍。
5. 代码现场：定位到方法级 + 行号范围，只给文件名不算数；<debug 场景追加：再找一遍
   有没有形状相同的其它位置——同一个错误码 / 校验 / 文案是否在别处也复制了一份，这一步
   必须在给出结论前做完，不要等实现完了再找>。

代码不在本仓（属于别的服务 / 外部平台）导致查不到很正常，如实标注"代码侧不可查，
本次只三方印证，置信度较低"，不要因为缺一路就补一个假结论去凑齐。

每条结论要能核实：`path/to/file:行号` + 关键内容逐字摘录。说"未找到"之前，先用一个
你确知存在的东西验证一下检索手段本身有效，避免把"搜索姿势不对"当成"真的没有"。

遇到两个信源明确互相打架：不要自己选边，原样并列写出分歧，标"待人拍板"。
遇到表述含糊（如"合适的宽度"）：可按项目里的既有先例理解，但要写清楚"我这样理解了，
依据是哪条先例"。遇到所有信源都没提过的地方：不要凭直觉编一个行为，写"没有任何来源
提及，需要人确认"，不要自己补一个看似合理的默认值。

不需要做：不产出销账表或事后核对报告；不判断这次要不要走这套收集流程（派你来之前
已经判断过了）；implement 场景不必做第 5 条同构检索；不要给整改建议。

【期望输出】
- 断言清单：逐条列出"这个功能单元受什么约束"，每条给来源坐标（`path:行号` + 摘录）
  与命中 / 未命中 / 本项目不存在这类信源 的判定。
- 分歧与空白：矛盾（两方打架）、含糊（可理解但要声明依据）、空白（无人确认）三类
  分开列，不要混在一起。
- 收集缺口：哪类信源没查到、为什么、会影响哪些断言的可信度。
```

## 填占位符时最容易出错的一处：功能单元边界

边界的判据是**「哪些断言必须一起验证」**，不是「哪些代码放在一起」。

拆太粗（「导入模块」）会让 collector 拿回一份什么都沾一点的报告，哪条都不够深；拆太细
（「第 7 条错误提示」）会让跨条目的矛盾没机会被发现——两条提示文案互相冲突这件事，
只有把它们放进同一次收集才看得见。拿不准时偏细，然后派两个。

## 这份模板放弃了什么（拆 context 队列时的取舍，勿再加回来）

原 context-keeper 有一整套落盘产物：`context.md`（上下文包）、`ledger.md`（销账表，
由实现者事后逐行填）、`reconcile.md`（事后差异核对）。三者在本机 8 个真实项目里
**一次都没有被创建过**，实证见 `hooks/tests/run-tests.sh` 文件头「2026-08-18 摘除 H27」。

它们依赖的前提是「收集者与实现者是两个能持续对接的常驻角色」。v7 一条 issue 一个
keeper 实例之后，收集与实现落在同一个实例的同一段上下文里，中间不再有需要靠文件
传递状态的缝——销账表要填给谁看，答案是「填给三分钟后的自己」，于是没人填。

**如果哪天真需要一份可追踪的断言表**，那是 keeper 自己的产物（写进 `issue.md` 的一节），
不是 collector 的输出格式。别把它加回这份模板——collector 是一次性的，它交完就消失了，
不存在「日后回头核对」这个动作。
