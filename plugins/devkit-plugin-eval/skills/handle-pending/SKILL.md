# 处理待审（devkit-plugin-eval）

本插件只有一个 Python 命令行。每条命令都这样起头，下文简写为 `<pe>`：

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin_eval.py" --data-dir "${CLAUDE_PLUGIN_DATA}" <子命令> ...
```

`--data-dir` 写在子命令**前面**。两个 `${...}` 在本 skill 加载时已替换成绝对路径，照抄这一行。
命令输出里给的下一步命令写的是 `python3 plugin_eval.py --data-dir '...'`，执行前把 `plugin_eval.py` 换成上面的完整路径。
参数以 `<pe> pending --help` 为准。

## 裁定只来自用户

待审页是用户终裁的环节：判分分歧、抽检、报告审阅、条款清单变更、草稿勾选、复盘候选选题，都由用户在页上选。回复码只写回用户贴来的那一串，原样整串传给 `--reply`。用户没贴回复码时，给页的位置、等用户去选。
理由：写回会把报告改成「已审」、把草稿移进正式用例、把裁定存成金标。AI 代选的裁定会被闸门当成用户审过的依据，后面没有任何一步能把它分辨出来。

**待审报告不能作为改插件或发版的依据。** 一份对照报告在用户审过、写回成「已审」之前，不据它的结论改插件、不据它判能否发布；用户问起时把这句告诉用户。

## 用户贴回回复码

回复码形如 `PE1 <run_id> <page_id> 1A 2B ...`。

1. 定插件名：回复码里没有插件名。用户这轮说了就用；没说时 `<pe> list` 看登记清单，只登记了一个就用它；多个时在各登记仓的 `plugin-evals/<插件>/runs/<run_id>/`（复盘页的 run_id 形如 `review-<日期>`，对应 `plugin-evals/<插件>/reviews/<日期>.json`）里找；找不到唯一的就问用户。
2. 写回：`<pe> pending <插件> --reply '<整串回复码>'`。
3. 退出码 0：转述每一项写成了什么，以及「改动的文件（相对被测仓）」。这些改动在被测仓里还没提交，提醒用户由他决定何时提交。按写回结果给下一步：
   - 报告审成「已审」：这份报告从此可作发版依据，可以跑闸门（run-eval）。
   - 草稿勾选通过、移进了 `evals/`：接着跑 `baseline` 判基线已满足（run-eval）。
   - 复盘候选选中「转草稿」：转给 run-eval 跑 `drafts from-review <插件>`。
   - 待审项里有「建议跑对照」：转给 run-eval。
4. 退出码 2：原样转述报错。通常什么都没写进去；报错里列出「已写成」的项时，前面那几项已写回，照报错的说法用同一串回复码重试。常见三种：
   - page_id 不是最新一页——之后又生成过新页，旧页作废，请用户在最新那页重选；
   - 这一页已写回过——同一页只能写回一次；
   - 格式不对、序号不在页上、选项码不对——请用户从页上重新复制整串。
   改回复码去「修」报错不在本 skill 的做法里：回复码代表用户的选择。

## 用户要看待审项

- 最近一次对照、条款清单或草稿运行的页：`<pe> pending <插件>`；指定某次运行加 `--run <run_id>`。
- 会话复盘的页：`<pe> pending <插件> --review`（缺省最新一份，可跟日期）。
- 输出「没有待审项」时，它会列出较早仍有待审项的运行与 `--run` 用法，照列给用户。
- 生成成功：把「待审页」路径与「浏览器打开」链接给用户，转述「本页 N 项（共 M 项待判…）」。每页最多 10 项、按 10 分钟内审完设计；没上页的项留到下一页，抽样规则写在报告的「待审页抽样」一节。
- 每次生成都会让上一页作废：用户手里已有一页、还没贴回时，别为了「刷新」再生成一次。
- 页上的草稿带「隐私：由本机真实会话改写，通过前逐字审隐私」一行时（`review-*` 草稿），提醒用户通过前逐字看 prompt、历史、grader、文件桩；通过后它进 `evals/`、会随被测仓提交。
