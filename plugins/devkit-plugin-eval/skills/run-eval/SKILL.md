# 跑评测（devkit-plugin-eval）

本插件只有一个 Python 命令行。每条命令都这样起头，下文简写为 `<pe>`：

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin_eval.py" --data-dir "${CLAUDE_PLUGIN_DATA}" <子命令> ...
```

`--data-dir` 写在子命令**前面**（它是顶层参数）。两个 `${...}` 在本 skill 加载时已替换成绝对路径；Bash 工具的进程环境里没有这两个变量，所以照抄上面这行，不要改成读环境变量。
命令输出里给的下一步命令写的是 `python3 plugin_eval.py --data-dir '...'`，执行前把 `plugin_eval.py` 换成上面的完整路径。
子命令的参数以 `<pe> <子命令> --help` 为准，本 skill 不重复。

## 跑离线对照

1. **确认已登记**：`<pe> list`。被测插件不在清单里时，先向用户要被测插件所在仓的根目录，并把「登记即声明信任该插件，之后每次对照以用户身份运行插件代码与用例的 scaffold 脚本」告诉用户，用户同意后才 `<pe> register <插件名> --repo <仓根>`。登记是信任决定，由用户做。
2. **确认有用例**：看 `<仓根>/plugins/<插件>/evals/`（插件就是仓根时为 `<仓根>/evals/`）下有没有用例目录。没有用例时 compare 会直接报错，先走冷启动：
   - 尚无 `<仓根>/plugin-evals/<插件>/clauses.json` 且插件有常驻注入：`<pe> clauses <插件>`，出页后交用户审（handle-pending）。
   - `<pe> drafts write <插件>` 让 AI 起草用例，出页后交用户勾选（handle-pending）。
   - 勾选通过的草稿移进 `evals/` 后，`<pe> baseline <插件>` 判哪些用例「基线已满足」。
3. **选臂**：默认什么都不传。CLI 按 spec 的基线规则自动定臂——改版比上一版（沿 git 历史取版本号不同的最近一版）；新插件或从没升过版本号时上一版臂退化，只比「不装」与「当前版」，原因写在报告首段。只有两种情况改默认：用户点名要比某个版本或提交，传 `--base`；用户要复现与别的插件的冲突，传 `--env-plugin`。
4. **前置检查**：`<pe> check <插件>`（带上第 3 步决定的 `--base` / `--env-plugin`）。几秒出结果；退出码 2 表示硬项失败，原样转述失败项、停下，修好再跑。
5. **开跑**：`<pe> compare <插件> ...` 用 Bash 的 `run_in_background` 放后台。它每例每臂跑 3 次、真调模型，通常要几十分钟；告诉用户已在后台跑、跑完会汇报，然后可以接着做别的事。
6. **收尾**（后台任务结束后）：
   - 转述终端摘要（规则分、差、AI 评委一行、完整与否）。
   - 不完整（退出码 3）：转述「不完整原因」。撞订阅用量限制、超时这类原因可续跑：把输出给的 `resume <运行目录>` 命令交用户决定何时跑，续跑同样放后台。续跑成功会自动生成待审页。
   - 完整：`<pe> pending <插件>` 生成待审页，把输出里的「待审页」路径与「浏览器打开」链接给用户，请用户在页上选完、复制回复码贴回对话；之后的写回归 handle-pending。
   - 告诉用户：**待审报告不能作为改插件或发版的依据**；用户在页上审过、写回成「已审」才算数。报告结论在已审之前，不据它改插件、不据它判能否发布。

## 其余跑动作

| 动作 | 何时 | 命令 | 之后 |
|---|---|---|---|
| 会话复盘 | 用户要求；或对照、闸门输出提醒「超 7 天先复盘」 | `<pe> review`（放后台） | 输出给出复盘待审页命令（`pending <插件> --review <日期>`），出页后交用户 |
| 发版闸门 | 用户发版（推 main）前 | `<pe> gate <插件目录>`；退出码 0 过闸、1 未过闸 | 输出给出「跑规则子集」一行时，告诉用户这一步真调模型，同意后加 `--run-subset` 放后台重跑；输出说需要已审的离线对照时（major 升版、`eval-required:` 声明的版本），走上面「跑离线对照」 |
| 起草用例 | 冷启动；条款「无用例」；复盘候选转草稿 | `<pe> drafts write <插件>`（放后台） | 出页后交用户勾选 |
| 基线判定 | 新用例进了 `evals/` 之后 | `<pe> baseline <插件>`（放后台） | 判为基线已满足的用例只作回归守护用例 |
| 首次抽条款清单 | 插件尚无 `clauses.json` | `<pe> clauses <插件>` | 已有清单时它会拒绝，重抽是 compare 的第一步 |
| 前置检查 | 想先看环境是否就绪 | `<pe> check <插件>`；复盘前 `<pe> check --review` | — |

耗时长的命令一律放后台：真调模型的 compare、resume、drafts write、baseline、clauses、`gate --run-subset`，以及要扫全部本机会话记录的 review。

## 原样转述的提示

下面这些提示由 CLI 按实测数据算出，带着判断依据。转述时逐字照搬，并把它要求的下一步交用户决定：

- 「建议跑对照（会先更新条款清单）」——gate 输出、复盘结果与复盘待审页里都可能出现。
- 「距上次会话复盘…超过 7 天：建议先跑会话复盘」与「还没有会话复盘记录」——compare 写在运行日志（stderr），gate 写在输出里。
- 「（不含 N 个回归守护用例）」——跟在规则差、评委差后面。臂分含这些用例、差不含，所以两臂分数相减不等于差；省掉这句会让用户误读。
- 「threshold=…：每例全部 run 都过」或「…低于默认 1.0」——gate 与规则子集的通过口径。
- 「上一版臂已退化：…」「跨改名」「条款清单待确认」——报告能比到什么程度的限定。
