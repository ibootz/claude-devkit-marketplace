# 提示词工程 - Prompt Engineering

为命令、钩子、技能、子代理或其他 LLM 交互设计、评审、迭代生产级提示词，改进输出质量。

## 核心能力

### 1. Few-Shot Learning（少样本学习）

用示例而非规则教模型：2-5 个输入-输出对，展示期望行为，用于统一格式、特定推理模式或边界情况处理。

```markdown
从支持工单中提取关键信息：

输入："我的登录不工作，一直收到 403 错误"
输出：{"issue": "authentication", "error_code": "403", "priority": "high"}

输入："功能请求：在设置中添加暗黑模式"
输出：{"issue": "feature_request", "error_code": null, "priority": "low"}

现在处理："无法上传大于 10MB 的文件，超时"
```

### 2. Chain-of-Thought（思维链）

在最终答案前请求逐步推理：加一句"让我们一步步思考"（零样本），或给出带推理轨迹的示例（少样本）。

```markdown
分析此错误报告并确定根本原因。

逐步思考：
1. 预期行为是什么？
2. 实际行为是什么？
3. 最近有什么变化可能导致这个问题？
4. 涉及哪些组件？
5. 最可能的根本原因是什么？

错误："昨天部署缓存更新后，用户无法保存草稿"
```

### 3. 提示词优化

从简单版本开始，测量准确性/一致性/token 使用，逐步迭代——每次只加一个约束，才能判断是哪个改动带来的效果变化：

```markdown
版本 1（简单）："总结这篇文章"
→ 结果：长度不一致，遗漏要点

版本 2（加约束）："用 3 个要点总结"
→ 结果：结构更好，但仍缺少细节

版本 3（加推理）："识别 3 个主要发现，然后总结每个"
→ 结果：一致、准确、捕获关键信息
```

### 4. 模板系统

用变量、条件部分、模块化组件构建可复用提示结构：

```python
template = """
审查这段 {language} 代码的 {focus_area}。

代码：
{code_block}

提供以下方面的反馈：
{checklist}
"""

prompt = template.format(
    language="Python",
    focus_area="安全漏洞",
    code_block=user_code,
    checklist="1. SQL 注入\n2. XSS 风险\n3. 身份验证"
)
```

### 5. 系统提示设计

设置在对话中持续存在的全局行为约束：角色、专业水平、输出格式、安全底线。

```markdown
系统：你是一位专注于 API 设计的高级后端工程师。

规则：
- 始终考虑可扩展性和性能
- 默认建议 RESTful 模式
- 立即标记安全问题
- 提供 Python 代码示例
- 使用早返回模式

响应格式：
1. 分析
2. 建议
3. 代码示例
4. 权衡
```

## 关键模式

### 渐进式披露

从简单提示开始，仅在需要时加复杂性：

1. **Level 1**：直接指令——"总结这篇文章"
2. **Level 2**：加约束——"用 3 个要点总结，关注关键发现"
3. **Level 3**：加推理——"阅读文章，识别主要发现，然后用 3 个要点总结"
4. **Level 4**：加示例——包含 2-3 个输入-输出对

### 指令层次

```
[系统上下文] → [任务指令] → [示例] → [输入数据] → [输出格式]
```

## 最佳实践

1. **具体明确**：模糊提示产生不一致结果（机制见上方"提示词优化"三版对比）
2. **展示而非告知**：示例比描述更有效（本文所有 few-shot/CoT/模板示例都是这条的应用）
3. **广泛测试**：至少覆盖典型场景、边界输入、易错输入三类差异较大的输入，只测一类无法暴露不一致
4. **快速迭代**：单次只改一个变量（约束/示例数/推理步骤），改两个以上出问题时分不清是哪个变量导致的
5. **监控性能**：能拿到真实输出时对比准确率、一致性、token 开销；拿不到生产数据时至少人工过一遍 3-5 个代表性输入再上线
6. **版本控制**：像对待代码一样对待提示词——改动前后各存一份，才能定位是哪次改动导致效果变化
7. **记录意图**：写明为什么用这个结构（如"这里加 CoT 是因为直接输出会跳过验证步骤"），下次改的人才知道能不能删

## Agent 提示设计

### 上下文窗口

200K token 是当前对话可用的全部预算，覆盖历史与你将生成的输出，且历史轮次不会自动裁剪——每加一轮都在挤占后面能用的空间。写提示词时把这个数字当刚性约束，而不是当背景知识来解释。

### 简洁是关键

提示词、命令、技能与 Claude 需要的其他一切共享同一个上下文窗口。默认假设 Claude 已经足够聪明——只添加它还没有的信息。写每一段前问自己：这段话值得它的 token 成本吗？

**好例子**（约 50 tokens）：

````markdown
## 提取 PDF 文本

使用 pdfplumber 提取文本：

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

**坏例子**（约 150 tokens，多余的是背景科普，Claude 本就知道）：

```markdown
## 提取 PDF 文本

PDF（便携式文档格式）文件是包含文本、图像和其他内容的常见文件格式。
要从 PDF 中提取文本，你需要使用库。有许多可用于 PDF 处理的库，
但我们推荐 pdfplumber，因为它易于使用并能处理大多数情况...
```

### 设置适当的自由度

根据任务的脆弱性匹配具体程度：

- **高自由度**（文本指令）：多种方法都有效，决策取决于上下文，用启发式引导
- **中等自由度**（带参数的伪代码/脚本）：存在首选模式，可接受一些变化
- **低自由度**（特定脚本，很少或没有参数）：操作脆弱、一致性至关重要、必须遵循特定顺序

## 说服原则

LLM 对与人类相同的说服原则有响应：研究表明说服技术使合规率翻倍（33% → 72%）。

1. **权威**：专业、凭证、官方来源——用命令式语言（"你必须""绝不""始终"），用于纪律执行技能、安全关键实践
2. **承诺**：与先前行动一致——要求公告（"宣布技能使用"）、强制明确选择（"选择 A、B 或 C"）
3. **稀缺性**：时间限制或有限可用性的紧迫感——"在继续之前"、"在 X 之后立即"
4. **社会证明**：符合他人所做或被认为正常的事——"每次""始终"，或反向"没有 Y 的 X = 失败"
5. **统一**：共享身份、"我们感"——"我们的代码库""我们是同事"，用于协作工作流、建立团队文化
6. **互惠**：回报收到好处的义务——仅在双方是对等协作（如"我已经帮你精简过示例，麻烦你也检查一下格式"）时使用；单向要求 Claude 遵从时会显得算计，不要用
7. **喜欢**：与喜欢的人合作的偏好——不用于换取合规，一旦被识别为讨好话术，会连带削弱同一份提示词里其余六条原则的可信度

## 原则组合

| 提示类型  | 使用                   | 避免       |
| --------- | ---------------------- | ---------- |
| 纪律执行  | 权威 + 承诺 + 社会证明 | 喜欢、互惠 |
| 指导/技术 | 适度权威 + 统一        | 重度权威   |
| 协作      | 统一 + 承诺            | 权威、喜欢 |
| 参考      | 仅清晰                 | 所有说服   |

## 伦理使用

**合法**：确保遵循关键实践、创建有效文档、防止可预测的失败

**非法**：为个人利益操纵、制造虚假紧迫性、基于内疚的合规

**测试**：如果用户完全理解这项技术的运作方式，它是否仍然符合用户的真正利益？不符合就不要用。
