# ultraverify：结论交付前的证伪内环

审查子代理核的是起草者给的出处，它会被锚定在起草者的证据上：起草读到 Service 层就停，审查也只读那几行 Service，两边都看不到 SQL 里那个 `relation_type != 1`。
本 skill 补上缺的那一环：**证伪者拿不到起草的证据和答案，只拿到问题，自己从源头推一遍。**两边推出的结论不一致，就是**红**。

一次运行就是一条结论走一遍下面的步骤。调用方（另一个 skill 或主会话）提供领域的东西；本 skill 只管流程、留痕和停止条件。调用方要提供什么，见 [`references/contract.md`](references/contract.md)。

## 第 0 步：建运行目录

运行目录用调用方给的；没给就新建 `${CLAUDE_JOB_DIR:-$TMPDIR}/ultraverify/<YYYYMMDD-HHMMSS>/`。
每轮建一个子目录 `round-<N>/`，本 skill 产生的每个文件都写在里面。留痕的用处是：事后能查清每一轮红在哪条、为什么改。
**完成判据**：目录存在，`input.md` 里写好问题原文、待证结论（原稿全文或路径）、调用方给的源头清单、预算与「判档基准时点」（调用方没给就写「现网」）。

## 第 1 步：拆断言，挑要证伪的

把原稿拆成一行一条的事实断言，写进 `round-1/claims.md`，每行编号 `C1`、`C2`……
满足下面任一条的，标为 **高风险**：

- 写入、删除、覆盖、清空、「不会更新」这一类操作的后果；
- 能产生同一现象或报错的分支不止一个，而原稿只答了其中一个；
- 全称或否定的说法：都、全部、只有、不会、没有、不支持；
- 定性：是缺陷，还是设计如此、需求未覆盖；
- 时点：某个修复或改动在提问当时是否已上线；
- 调用方在 contract 里追加的领域触发条件。

一轮最多证伪 5 条高风险断言，超过就按「说错了谁受损最大」排序取前 5，其余写进 `claims.md` 的「本轮未证」一节。一条高风险断言也没有时，直接跳到第 5 步，结论写「无需证伪」，并列出逐条不命中的理由。
**完成判据**：每条断言要么标了高风险并给出命中哪一条，要么标了低风险；高风险的条数不超过 5，超出的已写明。

## 第 2 步：改写成盲问

每条要证伪的断言改写成一个**盲问**：只问事实，不带原稿的答案，不暗示哪边对，也不写原稿引用的文件和行号。写进 `round-<N>/questions.md`。

| 原稿断言 | 盲问 |
|---|---|
| 重新发起测评会删掉旧的评估关系，自评也一起删 | 重新发起测评时，已有的评估关系会被怎样处理？自评关系是否在处理范围内？追到实际执行的 SQL 条件。 |
| 指标库的「我创建的」筛选对管理员不生效，是缺陷 | 管理员勾选「我创建的」时，后端的过滤条件是什么？该行为在提问日期当时的线上版本里是什么样？ |
| 只有能力模型会出现在这个下拉里 | 这个下拉的数据来源接口按什么条件取数？哪些类型的对象会出现？逐个列出枚举值。 |

盲问里可以写现象、对象、提问日期和问的是哪个版本，这些是问题本身的一部分。
**完成判据**：逐条自查，每个盲问里没有原稿的结论词，没有原稿的出处路径，也没有「是否确实」「请确认」这类诱导性措辞。

## 第 3 步：派证伪者

每份待证稿派一个独立的证伪者（多份稿子就派多个，各用各的额度，不合给同一个），用宿主的子代理工具（Claude Code 里是 `Agent`；宿主起不了子代理时，把填好的证伪者 prompt 落盘，请用户在一个新会话里跑，回执写到 prompt 指定的产出路径），按 [`references/prompts.md`](references/prompts.md) 的「证伪者」模板填写 prompt。只给它这些：盲问、问题原文与提问日期、判档基准时点、调用方的源头清单与查询红线、产出路径。**不给**原稿、起草者的 evidence，也不给 `claims.md`。
模型可以换一个档位（比如起草用 sonnet，证伪就用 opus），这样两边的盲区更不容易重合；调用方没指定时用 opus。
证伪者要逐题作答，出处读到决定结果的那一层（SQL 的 where 条件、枚举定义、配置值、提交说明），每题落一个结论：确定答案加出处，或者「证实不了」并写明卡在哪一层。每题还要写明对照的是哪个版本或时刻，出处文件在基准时点之后有提交的，列出提交 hash 与日期。
**完成判据**：`round-<N>/falsify.md` 里每个盲问都有答案，每个答案都带出处或写明卡点。

## 第 4 步：比对，判红

逐条把证伪者的答案和原稿断言对照，写进 `round-<N>/verdict.md`，每条判一个档：

| 档 | 判据 | 处理 |
|---|---|---|
| 绿 | 两边结论一致，出处都能读到 | 保留 |
| 红 | 两边结论相反，或证伪者找到了原稿漏掉的分支或条件 | 回到源头读双方的出处，判谁对，写明判据；原稿错了就改稿 |
| 疑红 | 证伪者与原稿冲突，你已开始亲读证伪者的出处，但预算内没读完 | 按红处理：改稿，或进入第 5 步的升级；不得记成灰 |
| 灰 | 证伪者证实不了，或者两边各有出处、谁也推不翻谁 | 把这条断言改成条件式（「若……则……」），或者删掉 |

证伪结果与原稿冲突（相反、或证伪者多出分支或条件）时，**先打开证伪者给的出处（路径:行号）亲自读，读完再判红或绿**；这一步先于任何记灰，工具额度优先花在这里。预算内读不完的标「疑红」。证伪者与原稿冲突的断言不得记灰：灰只留给「证伪者自己证实不了」或「两边各有出处、谁也推不翻谁」。只凭证伪者的说法不改稿，它也会错。
`verdict.md` 开头写判档基准时点。证伪者标出「出处文件在基准时点之后有提交」的，在对应断言行注明提交 hash 与日期，并写明原稿的断言在基准时点前后是否一致。
有调用方给的审查清单时，用改好的稿子再过一遍清单（也可以派审查子代理，见 prompts.md 的「审查者」模板），清单驳回的理由一并写进 `verdict.md`。
**完成判据**：每条被证伪的断言都有档位；每条红都写了「谁对、依据哪几行」；每条冲突的断言都有「亲读了哪几行」或标了疑红；改过的稿子另存为 `round-<N>/draft.md`。

## 第 5 步：停止或升级

- 全绿，或者红、疑红和灰都已改完而且是同一轮确认的（疑红按红改）：**停止**，交付 `round-<N>/draft.md`。
- 本轮改稿时**新加了**高风险断言：进下一轮，只证新加的这几条，回到第 2 步。
- 已经跑满 2 轮，还有红或疑红没解决：**升级**。不交付这条结论，把未解决的那几条连同双方的出处交给调用方或用户拍板。
- 预算用完（见 contract 的预算一节）：按「升级」处理，写明用到了哪一步。

收尾时在运行目录根写 `summary.md`：跑了几轮、每轮证了几条、红几条疑红几条灰几条、最终是停止还是升级、交付稿的路径。回给调用方的就是这份 summary 的内容。
**完成判据**：`summary.md` 存在；结论是「停止」时交付稿里没有未处理的红；结论是「升级」时写明了要谁拍板、拍什么。
