# 调用方契约：跑一次 ultraverify 要提供什么

本 skill 不带任何领域知识。领域知识由调用方提供：可以是另一个 skill（比如某个答疑值守 skill 在审查之后接进来），也可以是用户在对话里直接要求。
下面每一项都写进运行目录的 `input.md`。缺了必填项先补齐再开跑，补不齐就向调用方或用户要。

## 必填

| 项 | 内容 | 缺了会怎样 |
|---|---|---|
| 问题原文 | 提问人的原话，带提问时间 | 盲问没有锚点，证伪者答的是另一个问题 |
| 待证结论 | 原稿全文或文件路径 | 没东西可拆 |
| 源头清单 | 证伪者可以读、可以查的东西：仓库路径、可用的只读命令、数据查询入口 | 证伪者只能凭记忆答，比起草者还弱 |

## 选填

| 项 | 默认 | 说明 |
|---|---|---|
| 查询红线 | 只读；不写任何外部系统、不发消息 | 调用方有更细的红线（如查库必带租户条件、LIMIT 上限、日志时间窗）的，原文照抄进证伪者 prompt |
| 领域触发条件 | 无 | 追加到第 1 步的高风险判据后面，例如「涉及计费金额」「涉及权限放行」 |
| 审查清单 | 无 | 第 4 步改稿后用它再过一遍；路径或全文都行 |
| 起草者的 evidence | 无 | **只给审查者，绝不给证伪者** |
| 禁读清单 | 无 | 证伪者不许读的文件（例如评测时据同一道题写下的答案）。光在 prompt 里写「不许读」挡不住检索结果里的摘要行，能从检索范围里移出就移出 |
| 证伪者模型 | opus | 与起草者不同档位更好 |
| 预算 | 每轮 1 个证伪者；每个盲问约 15 次工具调用，单个证伪者合计不超过 60 次；最多 2 轮 | 额度按盲问给，不写「共 N 次」，否则排在后面的题会被挤掉 |
| 运行目录 | `${CLAUDE_JOB_DIR:-$TMPDIR}/ultraverify/<时间戳>/` | 评测或批量跑时由调用方指定，便于事后汇总 |

## 从另一个 skill 接进来

在调用方 skill 的流程里，审查通过、准备交付之前，加这样一步（措辞按调用方的文风改）：

```
结论命中下列任一条时，先加载 devkit-ultraverify:ultraverify，按它的流程证伪后再交付：
<调用方的领域触发条件>
源头清单：<路径与命令>；查询红线：<原文>；审查清单：<路径>；运行目录：<路径>。
ultraverify 的结论为「升级」时，不交付，按本 skill 的升级路径处理。
```

调用方不需要改自己的审查步骤。ultraverify 是叠加在审查之后的一层，不替代审查：审查查的是「出处对不对得上」，证伪查的是「不看出处，能不能独立推出同一个结论」。

## 批量跑（评测用）

拿一批已有的稿子测证伪环节能不能抓住已知错误时：

1. 每份稿子一个运行目录，各自跑第 1 到第 4 步；
2. 多份稿子可以合给同一个证伪者，但盲问按稿子分节，额度按盲问给；
3. 汇总时分两组数：**命中**（已知错误被判红）和**误报**（判红了，但回到源头核实后原稿是对的）。误报和命中一样要回源头核实，不能只看证伪者怎么说。
