# devkit-ultraverify

一个结论交出去之前，派一个看不到原稿证据的子代理，独立从源头把关键断言再推一遍。推出来不一样就改稿，两轮还证不实就交给人拍板。

## 怎么开

| 方式 | 写法 | 效果 |
|---|---|---|
| 关键词 | 提示里任意位置写 `ultraverify`，例如「查一下这个接口会不会删自评 ultraverify」 | 本轮注入一段话，让 AI 交付前加载 skill。只对当轮有效 |
| 直接调 skill | `/devkit-ultraverify:ultraverify` | 同上 |
| 自然语言 | 「证伪一下」「独立复核这个结论」 | 靠 skill description 触发，不保证每次都触发 |
| 另一个 skill 调用 | 在那个 skill 的流程里写「命中某某条件时加载 devkit-ultraverify:ultraverify」 | 见 `skills/ultraverify/references/contract.md` |

关键词借鉴 Claude Code 内置的 `ultrathink`：选一个日常用语里不会出现的英文词，写进提示就开启。反引号里的 `ultraverify` 不算，这样讨论本插件时不会误开。

## 它解决什么

普通审查核对的是起草者给的出处，审查者看到的证据和起草者一样多，也就跟着起草者在同一层停下。
实例：起草者读到 Service 层，判断「重新发起会删掉全部评估关系」；审查者打开同一段 Service 代码，对得上，放行。真正执行的 SQL 里还有一个 `relation_type != 1` 条件，自评其实不删。两个人都没读到那一层。

本插件的做法是把断言改写成不带答案的「盲问」（「重新发起时，哪些评估关系会被处理？追到 SQL 条件」），交给一个拿不到原稿和证据的子代理去答。它没有现成的停止点可以跟，只能自己追到底。

## 流程

1. 把原稿拆成断言，挑出高风险的（删除覆盖类、多分支、全称否定、缺陷定性、修复时点），一轮最多 5 条；
2. 把这些断言改写成盲问；
3. 派证伪者独立作答，答案要带出处，答不出写卡点；
4. 逐条比对，判绿、红、疑红、灰。与证伪者冲突的先亲读证伪者的出处再判，读不完记疑红并按红处理；灰的改成条件式；判档基准时点由调用方给，未填默认现网；每份稿子配独立证伪者与独立额度；
5. 全部处理完就停止；新加了高风险断言就再跑一轮；跑满 2 轮仍有红就升级给人。

每一轮的盲问、作答、判定都留在运行目录里。

## 不做什么

- 不替代审查。审查查「出处对不对得上」，证伪查「不看出处能不能推出同一个结论」，两者叠加。
- 不带领域知识。证伪者能查哪些仓、哪些库，查询红线是什么，由调用方给。
- 不做外环评测（固定题集回放、打分、归因）。那部分目前留在使用它的领域 skill 里。
