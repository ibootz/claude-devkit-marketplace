# 事实底稿与写篇子代理

第 3、4 步的规程。事实底稿是各篇子代理唯一共同的底本：子代理之间看不到彼此，术语、数字、图的风格能统一，全靠它。

## `01-fact-base.md` 模板

```markdown
# <新事物名>：事实底稿

**档位**：速览 / 标准 / 深入　**进步陈述**：<一句话>
**使用者背景**：<做什么的>；可借力的已知：<…>；可能误导的已知：<…>
**新事物类型**：系统 / 业务 / 理论 / 组织（可多选，主类型写第一个）

## 术语
| 术语 | 白话定义 | 原名与别名 | 出处 |

## 关键事实
| 编号 | 事实 | 标签 | 出处 |

## 篇目分工
| 篇号 | 篇位 | 回答什么问题 | 目标理解层级 | 重访的核心概念 | 计划的图 |

## 图规约
- 风格：<rounded-sans 默认；术语里标识符多时用 mono>
- 角色配色：<新事物本身 / 使用者已知的东西 / 外部参与方 / 风险与空白，各用哪组 fill 与 stroke>
- 图例：每篇第一张图下放图例，写颜色、线型、缩写各代表什么。
- 文件名：figures/<篇号>-<主题>.excalidraw 与同名 .png
```

**目标理解层级**取三级之一：能列出要点 → 能讲清要点之间的关系 → 能迁移到新情境。全组文章覆盖三级，不全停在第一级。

**重访的核心概念**：每个核心概念至少在两篇里出现，从不同案例或不同表征（表格、图、例子、反例）切入。分工表要能看出各篇怎么互补、怎么互相约束。

## 写篇子代理的派发说明

每篇一个 `general-purpose` 子代理，模型取 sonnet；机制篇题材复杂时取 opus。第一批同一条消息并发派出，融会贯通等第一批交回再派。派发 prompt 含四段：

- 【目标】写 `<篇号>-<篇位>.md`（交付格式是 HTML 时写正文片段 `<篇号>-<篇位>.html`，片段里的 `id` 以篇号开头），回答分工表里本篇那一行的问题，达到本篇的目标理解层级。
- 【上下文】
  - 必读：`01-fact-base.md` 全文、`00-sources.md` 的冲突清单、本 skill 的 `references/articles.md` 里本篇篇位那一节。
  - 写作：先调 `devkit-tool:tech-doc`，按它判类型、套骨架、自检；交付格式是 HTML 时另读它的 `references/html.md` 第三、四、七节（标签写法、配图、片段约定），篇间链接写 `<篇号>-<篇位>.html#id`。
  - 画图：调 `devkit-excalidraw-diagram:excalidraw-diagram` 出图，按事实底稿的图规约配色与命名；渲染后 Read PNG 检查，有缺陷就改；核对 PNG 修改时间晚于本次渲染开始，渲染命令不接 `tail`、`head`；跑不通就原位放文本箭头图、标「待补 Excalidraw 图」与原因。
  - 资料原文的路径，供核对出处时回读。
- 【约束】
  - 术语与数字以事实底稿为准。发现事实底稿有错或缺，不自行改它，写进回执。
  - 每条事实带来源标签与出处；底稿里没有、资料里也查不到的，标【空白】。
  - 不执行 `open`、`start`；不提交。
  - 本篇时间上限：标准档 20 分钟、速览档 12 分钟，到限就交回已写部分并写明缺什么。
- 【期望输出】回执只写：文件路径、图的路径与张数、标「待补」的图及原因、发现的事实底稿问题、【空白】项。不贴正文。

融会贯通的子代理另加：必读第一批全部文章，引用它们时写相对链接。

## 主会话收回执时

- 第一批里导读、本质先到时，立即告诉使用者可以开始读。
- 回执报了事实底稿问题的，主会话核实后改底稿，再判断哪几篇要跟着改。
- 在 `run-log.md` 记每篇的派出与交回时刻。
