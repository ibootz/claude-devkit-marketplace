# Bucket Audit — 大头桶定性核实

## 这个 skill 防什么

启发式分桶（按关键词/路径/正则匹配）产出的桶名，写进报告后会被当成事实。名字携带的机制定性（"这是在写后回读"）与桶内实际内容可以完全不符，且全程无报错——条数对得上、桶名完好，坏的只是"名字 ↔ 现实"的对应关系。下游的裁剪项、可省比例、ROI 系数全部建在这个名字上，定性错则整条决策链错。

（实证起源：2026-08-28 一次耗时分析报告。351 条 / 3.49h 的桶按路径关键词被命名为「回头核自己刚写的账本与规格」，定性"写后回读"，据此写了"放宽写后回读纪律"的裁剪项。全量导出归类后：定位条款 56.1%、复算条数与哈希 23.1%，字面的"写后确认落盘"最宽口径仅 18.2%、紧口径 10.5%。桶名与报告数字全程无报错，错的只是名字与现实的关系。）

## 触发判据（满足任一）

1. 统计报告里按关键词启发式分的桶占大头（条数/工时/金额前列），且其定性将被用于决策
2. 下游已有决策（裁剪清单 / ROI / 优化方案）建在某个桶的定性上
3. 听报告的人可能追问"为什么这么多 / 这里面到底是什么"
4. 桶名描述的是机制推断（"为什么要做"）而不是内容（"碰的是什么"）——这本身就是红旗

## 什么时候不触发

- 桶小（占比 < 5% 且无决策依赖）——核实成本高于收益，标注"启发式命名、未核实"即可
- 桶名描述客观内容（如"管 git / worktree / 子模块"）且无决策依赖
- 定性已有一手证据支撑（真正读过桶内全部条目，而非凭名字或抽样印象）

## 流程（八步，顺序固定）

### 1. 评估下游暴露面
先回答：**这个桶名的定性如果错了，哪些下游结论要跟着改？**
- 列出建在这个定性上的每个下游产物（裁剪项、系数、结论段落）
- 暴露面越大，核实的深度要求越高。无下游依赖的桶，核实到"读 10 条样本"即可
- 这一步的产出是一份清单，供第 8 步逐项回改

### 2. 复现定义
从代码里找到生成这个桶的函数（`classify` / `bucket_of` / 正则表），抄下判据原文，用同一套代码在原窗口重跑一遍，**精确复现条数与工时**。目的：证明对判据的理解无误，后续所有结论站在"判据被正确复现"上，不是凑出来的数字。

### 3. 回原始数据（防截断）
检查中间数据文件有没有截断字段（如 `cmd` 截到 200 字符）。有截断就回 raw transcript（`~/.claude/projects/<项目>/*.jsonl`），按时间戳（毫秒级）精确匹配重扫，拿未截断全文。**截断字段上的归类结论只对"截断后仍可见的部分"成立，对大头桶不可接受。**

### 4. 精确对账
全量条数必须与统计数字**严格相等**。不等就先解释差在哪（时间窗口、判据版本、fallback 命中数），对上之后才准往下走。禁止"大致对上"。

### 5. 检索手段自证
采信任何"没有 / 零命中"之前，用已知存在的串试搜并确认命中。附上命中计数作为管道有效性证据（如"`worktree` 命中 332 次"）。能做正面列举（把某一节整个抽出来）时优先正面列举，不用否定检索。

### 6. 全量归类（禁止抽样代替全量）
以条目**自带的自我描述**为主信号（工具调用的 `description` 字段、命令里的 `echo "=== 意图 ==="` 标记——这是执行者自己写的意图说明），辅以结构特征，按固定优先级一次打标：

| 优先级 | 信号 | 典型形态 |
|---|---|---|
| 1 | 自描述 | `description` 字段、`echo "=== ... ==="` |
| 2 | 结构特征 | `grep -n`/`sed -n` 单文件定位→定位类；`grep -c`/`wc -l`/`shasum`→计数类；跨 ≥2 文件核对同一件事→交叉核对类 |
| 3 | 抽读校准 | 每类抽 5~10 条人工读原文，校准规则后再全量打标 |

**禁止抽样代替全量**：抽样的前提是条目同质，而"桶名 vs 内容"的错位恰恰说明不同质。允许个别边界命令误分到相邻类，只要方向性结论不受影响（在回执里说明噪声边界）。

### 7. 时间关联检验（检验桶名暗示的成因）
把桶名暗示的机制转成可机械判定的关联判据，穷举全量（非抽样）：

- 例："写后回读" → "目标文件在命令执行前 ≤N 秒内刚被 Write/Edit 过"
- 跑**宽/紧双窗口**（如 ≤600s / ≤60s）各出一个占比上界
- **人工读紧窗口命中的样本原文**，判断命中者是否真是那个机制——时间相邻 ≠ 因果（紧窗口的命中多数可能是结构校验，不是朴素回读）
- 产出：机制成立的占比上界（宽/紧两档），与桶名定性对照

### 8. 产出与改正

**结论三件套**：
1. 分布表（每类条数 + 占比 + 3 条截断原文示例）
2. 一句话结论（大头是什么、桶名定性成立与否、宽/紧上界）
3. 追踪交代——实际追到哪一层、哪些边界没追（例：只读了命令原文判断意图，未打开被检索的目标文件核对内容是否正确）

**定性被推翻时，改正三件套**（顺序固定）：
1. **改数据层**——桶名与机制说明改在生成统计的数据层脚本里，不在展示层改字。展示层只读数据层产出的 json，只改展示层会出现"图上改名了、底稿还是旧名"的分叉
2. **按实证加权重算下游系数**——可省比例 = Σ(该类占比 × 该类可省比例)，每类的可省比例单独给理由，**禁止再拍一个总折扣**。重构后的方案要重讲：为什么数字近似但解法换了
3. **留改正记录**——交付物里写明：原定性是什么、错在哪、依据什么改正、下游哪些结论跟着变了。改正记录放在报告正文相关条目旁，不藏进附注

## 桶名纪律（预防，比核实便宜）

起桶名时只描述**内容**（"碰的是什么"），不描述**机制推断**（"为什么要做"）。"在自己写的账本与规格里定位与复核"是合格的；"回头核自己刚写的账本与规格"是越界的——"回头核"是对动机的断言，不是对内容的描述。

## 派子代理执行时的约束段写法

导出与归类是大输出任务（读 raw transcripts、几千条命令全文），**派 Explore 子代理**，主会话只收三件套。子代理 prompt 的【约束】必须写死：

- 全程只读，中间产物只准写指定 tmp 目录，禁止改仓库文件
- 追踪停止条件：**追到"命令原文能看出在核什么"为止**；不打开被检索的目标文件核对内容正确性（那是另一层）
- 读不到的写"未找到"，禁止推断；撞守卫即停手

【期望输出】写死：三件套 + "实际追到哪一层、哪些边界没追"。

## 与其他纪律的关系

- 「写后回读」管的是**外部系统**写（2xx ≠ 字段生效），本 skill 管的是**统计定性**的核实，两者经常在同一次分析里相邻出现但互不覆盖
- 与「静默失效的引用」同族：桶名自身完好、检索有结果，坏的只是名字与现实的对应关系，失效不报错
- 派发约束见 working-discipline 5.6（停止条件、结构化回执、归因不可直接抄——子代理报的"因为 X 被拦"要自己复现一次才准写进文档）
