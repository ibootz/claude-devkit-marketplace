# 技术文档（写给人读的 md）

本 skill 管一篇文档的**类型、骨架、写法、配图、自检**五件事，按顺序做。
单张图怎么画、放哪交给 `devkit-tool:show-me`；要 Excalidraw 成品图交给 `devkit-excalidraw-diagram`（已安装时）；写给 AI 的文档归 `writing-for-agents`。

**读者假定**：懂开发，对本项目零上下文——不知道它做什么、有哪些参与方、内部叫法指什么。不按读者职位或此前提问推高这个假定。

规则后的 【有出处】【推断】【判断】 标的是依据强度，来源与原文在 [`references/sources.md`](references/sources.md)。

## 第一步：判类型

按**读者打开这篇时要什么**判，不按作者想写什么判。【有出处】Diátaxis 用两个问题分类：读者在动手做事还是在理解知识；在学新技能还是在用已有技能。本仓在其四类上补了三类常见产物。

| 读者此刻要什么 | 类型 | 骨架 |
|---|---|---|
| 跟着做一遍、学会一项新技能 | 教程 | doc-types.md「教程」 |
| 解决手上一个具体问题 | 操作指南 | doc-types.md「操作指南」 |
| 查准确事实：接口、字段、配置、清单 | 参考 | doc-types.md「参考与 API 参考」 |
| 理解为什么这样、各部分怎么关联 | 解释 | doc-types.md「解释」 |
| 一个问题的结论与证据：调研、核实、评估、盘点 | 分析报告 | doc-types.md「分析报告」 |
| 一项改动等拍板 | 设计文档 / 方案 | doc-types.md「设计文档与方案」 |
| 进入一个项目或一组文档的入口 | README / 导读 | doc-types.md「README 与导读」 |

**混合时定一个主类型**，其余内容按性质归位：
- 参考性质的（全量清单、术语表、出处索引、长表）移到文末附录。【有出处】Diátaxis 要求解释类 *closely bounded*。
- 服务另一个独立目的的，拆成单独文件，正文用链接引。【有出处】Kubernetes：一页只做成一件事，背景知识链接到 Concept 页。
- 给 AI 的指令（路径约束、调用哪个 skill、工作单）拆到单独文件，人读入口里不出现。【判断】

**完成判据**：能写出一句「这篇是 X 类，读者读完能 Y」。写不出来，说明这篇在服务两个目的，先拆。

## 第二步：套骨架

读 [`references/doc-types.md`](references/doc-types.md) 里对应那一节，照它排章节。各类骨架共用下面这个外框（教程、操作指南、参考按其骨架裁剪）：

1. **标题**：说清回答什么问题，不写成主题词。
2. **编制说明**（一到三行）：日期、依据与范围、读者假定、与上一版的关系（如「只调整结构，事实沿用上一版」）。
3. **一句话**：这篇回答什么问题、结论是什么。【有出处】BLUF / Minto：结论先行，所有观点挂在一个中心论点下。
4. **怎么读**：多文件、或正文超过约五屏时给一张表——想知道什么 → 读哪一节或哪个文件。【判断】
5. **主体**：按类型骨架。
6. **收尾节**按类型取：未核实与没追的边界、风险、不做的事、下一步。
7. **附录**：术语表、全量清单、出处索引、完整大图。

## 第三步：写正文

逐条照做，每条都是生手读不懂的一个已知原因。

- **先全景后细节**：一句话 → 一张全景图 → 分块展开（每块先讲为什么，再讲是什么）→ 附录。【有出处】Google：先画全景，再画子系统；Diátaxis 解释类：交代背景与为什么。
- **术语先教后用**：每个术语、代号第一次出现时，先写它在业务上是什么，再括注原名；附录术语表供回查，代替不了首次出现时的那句白话。【有出处】Google：介绍术语时先定义，专家容易犯「知识的诅咒」；【有出处，二手】Mayer 预训练原则。「先业务含义、后括注原名」是本仓做法【判断】。
- **结论分组**：并列结论超过 5 条时归成 3 到 4 组，每组一个上层论点。【推断】依据 Minto 金字塔。
- **断言分强度写**：已证实（附出处）/ 推断（写依据与假设）/ 判断（经验看法）/ 未核实（给核实途径），同一句不混两类。【有出处】RFC 模板把未决问题列为固定章节。
- **反方必写**：方案类写缺点、备选方案、不做的事。【有出处】RFC 模板的 Drawbacks、Rationale and alternatives 是固定章节。
- **示例讲为什么**：示例说明为什么这样用，不只演示怎么调。【有出处】Rust API Guidelines C-EXAMPLE。
- **更正改回原处**：发现前文有误就改原句，不在后文追加「上面那条不准」——只读前文的人会一直拿到错的。【推断】依据 DORA 文档质量指标里的「准确」「随变更及时更新」。
- **排版**：一句一行、短句；同一小段的几行紧挨，小段之间空一行，大段之间用 `---`；行 × 列的对照写 markdown 表格，先后步骤写有序列表；每段把结论或关键数字加粗一两处。

## 第四步：配图

**图文按内容分工**，不是二选一。【推断】依据 Mayer 多媒体原则与 Google「一图一段」：
- 结构、关系、时序、状态：图承载主要信息，文字只补为什么与例外。
- 因果、取舍、结论、不确定性：只能用文字。

**该有图的地方**（命中即画）：
- 解释类与分析报告：至少一张全景图，放在「一句话」之后。
- 4 个及以上参与方之间的调用或数据流转；3 步及以上的跨服务先后步骤；3 个及以上分支的判断。
- 方案或改动使结构变化：改前、改后各一张。

**每张图都过这六条**，细则、选图表与统一配色见 [`references/figures.md`](references/figures.md)：
1. 先写图注再画图。【有出处】Google *write the caption first*（原文是 often helpful 的建议）。图注写成「图 N 说的是：……」放在图前。【判断】
2. 一张图的信息量不超过一段文字，超了拆成一张全景加若干子图。【有出处】Google。落到数量上，方框不超过 7 个。【判断】
3. 每条箭头标注含义。【有出处】C4 审查清单。
4. 第一张图下放图例：颜色、线型、缩写各代表什么。【有出处】C4。
5. 图紧跟着逐块解释它的文字；与要点无关的节点删掉。【有出处，二手】Mayer 就近原则、去冗余原则。
6. 全篇配图同一风格、同一套按角色配色、同一字体。【判断】

图的载体与落点按 `devkit-tool:show-me` 第二、三节定。

## 第五步：交付前自检

逐条过，每条写「过」或「不适用（理由）」，全过才交付。
- [ ] 能说出「这篇是 X 类，读者读完能 Y」。
- [ ] 开头有一句话结论；多文件或长文有「怎么读」表。
- [ ] 每个术语、代号第一次出现处有白话解释。
- [ ] 清单、术语表、出处索引、长表在附录，不在正文中间。
- [ ] 每个断言标了强度，未核实的有核实途径。
- [ ] 该有图的地方有图；每张图有前置图注、不超过 7 个方框、箭头全标注；首图下有图例；全篇风格与配色统一。
- [ ] 文中没有「上面那条不准」式的追加更正。
- [ ] 加粗写成 `**标签：** 正文` 或 `**标签**：正文`。`**标签：**正文`（结束的 `**` 前是全角标点、后面紧跟汉字）按 CommonMark 规则不渲染成粗体。
- [ ] 发布到在线文档平台后回读一次：mermaid 显示成图而不是源码、粗体生效、没有 `&#42;` `\+` 之类转义残留、图片位置对。

## 评审或改写已有文档

1. 按第一步判它的主类型与混进来的类型。
2. 按第五步逐条过，每个问题写：位置（`文件:行号`）、问题、依据强度、改法。
3. 结论分三组输出：做到了的、问题、改法；先改生手入口（一句话、全景图、术语首次解释），再改其余。
