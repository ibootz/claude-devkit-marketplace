# 七类文档的骨架与写法原则

每节给两样：**骨架**（章节顺序）与**原则**（写法约束）。依据强度标注同 SKILL.md；来源原文见 [sources.md](sources.md)。

目录：教程 · 操作指南 · 参考与 API 参考 · 解释 · 分析报告 · 设计文档与方案 · README 与导读

---

## 教程

读者要跟着做一遍、学会一项新技能。

**骨架**【有出处】Kubernetes Tutorial 页（原文未写 must / should）：
1. overview：这一课做什么
2. prerequisites：前置条件
3. objectives：学完能做到什么
4. lessoncontent：编号步骤
5. cleanup：用编号步骤把环境恢复原状
6. whatsnext：接下来读什么

**原则**【有出处】Diátaxis 教程页：
- 一开始就告诉读者最后会做出什么。
- 每一步都有看得见的结果。
- 尽量少解释；解释链接到解释类文档。
- 不讲可选项与替代做法，只走一条路。
- 每次照着做都要能成功；步骤在真实环境里跑过一遍再交付。

## 操作指南

读者手上有一个具体问题，要把它做成。

**骨架**【有出处】Kubernetes Task 页：
1. overview：写清为什么要做这件事
2. prerequisites
3. steps：编号列表
4. discussion：展开 steps 里讲过的内容
5. whatsnext

**原则**：
- 一页只做成一件事；背景知识链接到解释类，不在本页重复。【有出处】Kubernetes
- 每步命令可原样复制执行；前置条件（在哪个目录、要什么登录态）写在命令上方一行。【判断】

## 参考与 API 参考

读者要查一个准确事实，不通读。

**API 参考骨架**【有出处】OpenStack（单个项目的惯例）——每个接口依次：
1. 标题
2. 方法与 URL
3. 描述
4. 成功状态码、错误状态码
5. 请求：参数表 + JSON 示例
6. 响应：参数表 + JSON 示例

URI 由宽到窄排（`/servers` 在 `/servers/{id}` 前），同一 URI 下按 GET、POST、PUT、PATCH、DELETE 排序。

**原则**：
- 每个公开项附一个示例，重点说明为什么要用它。【有出处】Rust C-EXAMPLE（should 级）
- 失败情况按情形写小节：会返回错误的写 Errors，会 panic 的写 Panics，unsafe 函数写 Safety。【有出处】Rust C-FAILURE（should 级）
- 枚举、状态码、标记位写「值(含义)」，含义取自定义处，不按字面猜。【判断】
- 结构与代码保持同构，按代码的模块划分排，不按作者的叙事排。【推断】

## 解释

读者要理解为什么这样、各部分怎么关联。架构说明、全景图、原理讲解都属这类。

**原则**【有出处】Diátaxis 解释页：
- 建立关联：讲这件事和别的事怎么连。
- 交代背景与为什么。
- 谈论主题本身，不夹操作步骤。
- 承认存在其他做法与观点。
- 收紧边界：解释类容易吸进操作步骤与技术描述，要挡在外面（原文 *keep explanation closely bounded*）。由此推出清单、长表、术语表不放正文。【推断】

**骨架**【判断】本仓样板（AI 基础设施全景图 v2）验证过的排法：
1. 编制说明（含读者假定）
2. 怎么读这份文档：想知道什么 → 读哪节
3. 一句话
4. 一、一张图看懂：图注 → 全景图（≤6 个方框，每条边标注）→ 图例 → 每个方框各一段解释 → 「容易误解的点」
5. 二、三……各子体系：每节先一张小图，再讲为什么、是什么
6. 交汇与关系：子体系之间的连接点，标证据强度
7. 风险与结构性发现
8. 未核实
9. 附录：术语表、全量清单、出处索引、完整大图

## 分析报告

读者要一个问题的结论与证据：调研、核实、评估、盘点、复盘。

**骨架**【推断】由 Minto 结论先行、RFC 未决问题一节、DORA「准确」指标合成：
1. 编制说明：问题从哪来、调查范围、数据截至何时
2. 一句话结论
3. 结论分组：3 到 4 组，每组一个上层论点，下列支撑要点
4. 证据：每条结论对应的数据、代码位置、来源，标强度
5. 没追的边界与未核实：实际追到哪一层、哪些没追、怎么核实
6. 建议与下一步：建议不写成定案
7. 附录：原始数据、出处索引

**原则**：
- 核实类结论写明停止条件：仅本文件内 / 追到直接调用方 / 追到跨服务边界。没写深度的结论视为未完成。【判断】
- 数字写明口径与单位，不同口径不混在一张表。【判断】
- 单份超过约 2 万字符时拆：结论与证据留主文，原始数据进附录或独立文件。【判断】

## 设计文档与方案

读者要判断一项改动该不该做、怎么做。

**骨架**【有出处】Rust RFC 模板（RubyGems 沿用，Unkey 用精简版）：
1. Summary：一段话说做什么
2. Motivation：为什么做、解决什么问题——模板称之为最重要的章节之一
3. Guide-level：站在使用者角度，假设已经实现，像教同事那样讲
4. Reference-level：站在实现者角度，讲边界情况与其他功能的交互
5. Drawbacks：缺点
6. Rationale and alternatives：为什么选这个设计、备选方案与为什么不选
7. Prior art：业界先例
8. Unresolved questions：未决问题
9. Future possibilities：将来可能的延伸

**原则**：
- 结构有变化就画改前、改后两张图。【判断】
- 「不做的事」单列一节，防止范围蔓延。【判断】
- 待拍板项写清起源、差距、影响范围、现场证据。【判断】

## README 与导读

读者刚进入一个项目或一组文档，要知道它是什么、从哪读起。

**README 骨架**【有出处】Standard Readme（顺序为 must 级）：标题 → 简短描述 → 目录（不到 100 行可省）→ 安装 → 用法（文档类仓库可省）→ 贡献方式 → 许可证（放最后）。横幅、徽标、背景、API、维护者为可选节。

**README 内容**【有出处】GitHub 官方文档（描述，非要求）：README 通常包含五项——项目做什么、为什么有用、怎么上手、去哪求助、谁在维护；只放上手与参与贡献必需的信息，更长的文档适合放 wiki。

**导读骨架**（一组调研、方案、票据的人读入口）【判断】本仓样板（人发 AI 混部前整备导读）验证过的排法：
1. 编制说明：日期、不引入新事实、AI 入口在哪个文件
2. 一句话
3. 怎么读这组文档：想知道什么 → 读哪个文件
4. 现状：全景图 → 图例 → 各块解释 → 对照表 → 容易误解的点
5. 目标：要收拾成什么样，改前改后对照图
6. 与相关方案的关系：一张关系图
7. 进度：已完成与待办各一张表，标阻塞关系
8. 需要先知道的风险
9. 不做的事

**原则**：
- 导读只做索引与全景，不复制子文档的结论细节，避免两处漂移。【判断】
- 给 AI 的入口（如 map.md）与给人的导读分成两个文件。【判断】
