# 内容研究写作助手

围绕主题做研究、拟大纲、改写引言、逐段给反馈，全程保留你原有的语气和风格，通过多轮迭代把草稿改到可发布状态。

## 适用场景

- 撰写博客文章、Newsletter、思想领导力文章、社交媒体二次创作
- 制作教育内容、教程、演示内容、课程大纲
- 研究并撰写案例研究、技术文档，需要带来源引用
- 改进开头/钩子，让读者愿意读下去
- 逐段获得反馈，为不同受众调整内容，迭代打磨草稿

## 开始一个写作项目

```bash
mkdir ~/writing/my-article-title && cd ~/writing/my-article-title && touch article-draft.md
```

用下面几个问题澄清项目——缺哪个问哪个，不必逐条发问：主题与主要论点、目标受众、期望长度/格式、写作目标（教育/说服/娱乐/解释）、已有研究或来源、期望的写作风格（正式/对话/技术）。

## 核心工作流程

### 1. 协作大纲

用户说"帮我创建一个关于 [主题] 的文章大纲"时，产出如下结构并标记待研究点：

```markdown
# 文章大纲：[标题]

## 钩子
- [开场白/故事/统计数据]
- [读者为什么应该关心]

## 引言
- 背景和上下文 / 问题陈述 / 本文涵盖内容

## 主要部分
### 第 1 节：[标题]
- 关键点 A / 关键点 B / 示例证据
- [需要研究：特定主题]
（可重复多节；至少一节安排反驳论点与应对方案，不要只堆正面论据）

## 结论
- 要点总结 / 行动号召 / 最后思考

## 研究待办
- [ ] 查找关于 [主题] 的数据
- [ ] [声明] 的来源引用
```

迭代时：根据反馈调整、确保逻辑流程、识别研究空白、标记需要深入研究的部分。

### 2. 研究并补引用

用户说"研究 [特定主题] 并在我的大纲中添加引用"时：搜索相关信息、找可信来源、提取关键事实与数据，按用户指定的引用格式（见"引用管理"节）写回大纲对应章节，注明"已添加到大纲第 N 节"。

引用前必须验证来源可追溯（能给出可查证的出处，不接受"研究表明"这类无来源断言）；时效类数据（市场规模、采用率、榜单）只用近 2 年内发布的版本并注明发表年份，历史类引用不受此限；有争议的论点至少呈现两方来源，不能只引用支持单一立场的证据。

示例产出：

```markdown
## 研究：AI 对生产力的影响
关键发现：
1. **生产力提升**：研究显示内容创建任务节省 40% 时间 [1]
2. **采用率**：67% 的知识工作者每周使用 AI 工具 [2]

引用：
[1] McKinsey Global Institute. (2024). "生成式 AI 的经济潜力"
[2] Stack Overflow 开发者调查 (2024)
```

### 3. 改进钩子

用户分享引言（如"这是我的引言，帮我让钩子更有吸引力"）时，按三个可检验特征逐条判断，不用"是否有吸引力"这类无法自检的问法：

- **信息缺口**：第一句是否留下一个具体的未解决问题，读者必须往下读才知道答案？若第一句是"本文将讨论 X"这类话题预告，判定不合格。
- **具体收益**：读者读完引言能否用一句"读完我会得到 ___"填空？只能填"更懂 X"这类抽象名词时判定不合格。
- **具体主体**：关键名词是否有可核实的主体（人名、机构、数字、年份），而不是"许多人""近年来"这类模糊指代。

按此结构输出：

```markdown
**当前钩子分析**
- 有效之处：[对应哪个特征成立]
- 可以更强的地方：[对应哪个特征不成立，及原因]
- 情感影响：当前 vs. 潜在
**建议替代方案**
选项 1（大胆陈述）：[示例] _为什么有效：对应哪个特征_
选项 2（个人故事）：[示例]
选项 3（意外数据）：[示例]
```

### 4. 逐节反馈

用户写完一节（如"我刚完成'为什么这很重要'部分，审查并给出反馈"）时，按固定模板给反馈；每条建议必须是"原文引用 → 具体改法"的配对，不允许"这里不够具体""这段可以更简单"这类没有落地动作的评语：

```markdown
# 反馈：[部分名称]
## 有效之处
- [具体是哪句/哪个论证起作用]
## 改进建议（清晰度 / 流畅性 / 证据 / 风格）
- [引用原文片段] → [具体改法]
## 具体行编辑
原文：> [草稿中的确切引用]
建议：> [改进版本]
原因：[解释]
## 需要考虑的问题
- [发人深省的问题]
```

若用户反馈请求笼统，引导对方换成更具体的问法：'这太技术化了吗？' '我担心这部分拖沓' '这在逻辑上流畅吗？' '还有什么方法可以解释这个？'

### 5. 保留作者声音

开始前鼓励用户提供 2-3 段过往写作样本并说明语气偏好，建立语气基准；给建议而非直接替换整段；用户明确说更喜欢自己的原版时采纳原版。检验"是否改过头"的方法：把改写后的句子放进用户原有样本的上下文里读一遍，若明显违和，说明改法偏离了原声音，需回退。

定期用以下问题校准，而不是自行猜测：这听起来像你吗？这是正确的语气吗？我应该更/更少（正式/随意/技术）吗？用户回"那听起来像我！"即为匹配，回"对我的风格来说太正式了"则说明改法偏离，需回退到更轻的版本。

### 6. 引用管理

按用户偏好使用以下三种格式之一，一篇文章内格式统一、不混用：

- 内联：`研究显示生产力提高 40%（McKinsey, 2024）。`
- 编号：`...40% [1]` + 文末 `[1] McKinsey Global Institute. (2024)...`
- 脚注：`...40%^1` + `^1: McKinsey Global Institute. (2024)...`

维护一份运行中的参考文献列表：

```markdown
## 参考文献
1. 作者. (年份). "标题". 出版物.
2. 作者. (年份). "标题". 出版物.
```

### 7. 最终审查

用户说"审查完整草稿的流畅性、清晰度和一致性"时，逐项给具体结论——不写"整体不错"这类无法定位问题的总评：

- 结构与流程：组织是否合理、过渡是否顺畅、节奏是否得当
- 内容质量：论点是否站得住、证据是否充分、示例是否有效
- 技术质量：语法与一致性、引用是否完整
- 可读性：句子是否有变化、段落长度是否合适——给结论必须指出具体卡壳在哪一句，不能只给"高/中/低"评分

附最终润色建议（引言/正文/结论/标题各给一条具体改法）与发布前检查清单：

- [ ] 所有声明都有来源
- [ ] 引用已格式化
- [ ] 示例清晰
- [ ] 过渡流畅
- [ ] 存在行动号召
- [ ] 校对拼写错误

## 按内容类型调整顺序

- **博客文章**：大纲 → 研究关键点 → 写引言→反馈 → 写正文各节→逐节反馈 → 写结论→最终审查 → 润色
- **Newsletter**：讨论钩子 → 快速大纲（短格式）→ 一次性起草 → 审查清晰度和链接 → 快速润色
- **技术教程**：大纲步骤 → 编写代码示例 → 添加解释 → 测试说明 → 补故障排除 → 最终审查准确性

## 文件组织

```
~/writing/article-name/
├── outline.md          # 大纲
├── research.md         # 研究和引用
├── draft-v1.md          # 第一稿
├── draft-v2.md          # 修订稿
├── final.md             # 准备发布
├── feedback.md          # 收集的反馈
└── sources/             # 参考资料
```
