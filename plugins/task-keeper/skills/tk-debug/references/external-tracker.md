# 外部工单回写：可插拔适配器契约

本文件定义 debug-keeper 在合并 + 实测通过后，把结果回写到**外部工单系统**（Jira、
GitLab issue、公司自建研发管理平台等）时要遵守的发现顺序与接口契约。

## 为什么要做成可插拔

task-keeper 是机构无关的通用插件，不知道也不应该知道使用它的团队具体接的是哪个
工单系统、那个系统的鉴权方式、字段命名、状态机长什么样。这些细节属于**机构自己的
插件**——它们清楚自己团队用的是哪个平台、有哪些内部约定。把回写逻辑写死在
task-keeper 里，换一个团队就要改代码；做成可插拔契约，机构侧只需要提供一个实现了
本契约的 skill，debug-keeper 就能在不知道对方细节的情况下调用它。

## issue frontmatter 里的 `external_ref` 字段

格式固定为 `<系统名>#<id>`，例如 `TRACKER#644168`、`JIRA#PROJ-123`、
`GITLAB#issues/456`。字段声明位置见 `hooks/lib/queue_files.py:84`（DEBUG 这个
`QueueSpec` 的 `fm_order` 里的一行注释），代码层面**不做前缀校验**——任何系统名
都可以写，识别与解析全部交给下面的适配器 skill 自己处理，本插件只负责「这个
字段存在」这一件事的判断。

## 三层适配器发现顺序

debug-keeper 需要回写某条 issue 的 `external_ref` 时，按下列顺序查找能处理它的
适配器 skill，命中即停止：

1. **项目配置声明**：读取项目根 `.claude/task-keeper.local.md`（**注意不是**
   `.keeper/` 下的任何路径。理由不是入库与否——v6 起 `.keeper/` 下多数内容已入库——
   而是**归属**：这份配置是项目级的、与具体交付无关，而 `.keeper/<交付id>/` 跟着交付
   走，交付 worktree 删掉它就没了）。若其中声明了
   `external_tracker_skill: <skill 名>`，直接用该 skill。
2. **按能力发现**：配置缺失时，遍历当前会话可用的 skill 列表，找 `name` 含
   `-writeback` 且 `description` 明确声明「实现 task-keeper 外部工单回写契约」
   的那个。
3. **都没有 → 报「未回写」，不阻塞**：在合并后回执里写「external_ref 存在但未
   回写（无适配器）」，并在该 issue「结局」章节记一句同样的话。**这不阻塞
   `status: done`**——代码已经修复合并，工单侧的回写是收尾锦上添花的动作，缺了
   它不该反过来卡住主流程。

## 适配器 skill 必须实现的契约

一个声明实现本契约的 skill，至少要能接受下面这组输入、完成下面这组动作、遵守
下面这组纪律：

**输入**：

- issue 文件的绝对路径（适配器自己去读 `external_ref`、「Triage」「修订记录」
  「验证」等章节提炼需要的内容，task-keeper 不做二次加工）
- 结局：`fixed` / `obsolete` / `duplicate` 三选一
- 一句话结论（供适配器自行决定怎么拼进目标系统的评论或字段）

**动作**：

- 把结局映射成目标系统对应的状态流转动作（映射规则由适配器自己维护，因为
  「已修复待部署」这类状态名在不同系统、不同项目模板里完全不同）
- 视目标系统能力追加评论、更新自定义字段等

**纪律**（不因为是外部插件就可以放松，反而因为是不可逆外部写要更严）：

1. **写前出示清单，等 Human 当轮授权**：不可逆的状态流转 / 评论追加，落地前
   一次性列出「工单号 + 动作名 + 内容全文」，等待明确确认再执行。
2. **写后逐字段回读**：2xx 响应不等于字段真的生效，写完立刻用只读接口把刚写的
   字段读回来核对。
3. **回执带回读到的实际值**：不是「已回写」三个字，而是「回读到状态=X」这类
   可验证的具体值。

这三条与 `references/queue.md` §6「外部工单回写」列的通用五步 / 三条铁律是同一套
纪律在两侧的呼应——task-keeper 侧描述"什么时候触发、找不到适配器怎么办"，适配器
skill 侧描述"接到活之后自己要守住什么"。

## 硬约束：通用侧不得硬编码机构专属发现路径

task-keeper 的任何文件（本文件、`queue.md`、`SKILL.md`、`agents/debug-keeper.md`）
**不得**出现类似「用 `find` 定位某公司插件下某个具体脚本」这样的指令——那等于把
一个机构专属依赖硬编码进通用插件。唯一允许持有的，是**配置里声明的适配器 skill
名**（一个字符串），具体那个 skill 装在哪个插件包、脚本长什么样，全部是它自己的
事，task-keeper 不关心也不应该关心。

## 参考实现

`radnove-core` 市场的 `debug-ones-writeback` skill 是一个把本契约接到 ONES
（一个研发管理平台）上的真实实现示例，可作为写新适配器时的参照。
