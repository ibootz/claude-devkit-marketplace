# 截图落盘：为什么必须主会话当场做，以及失败时怎么办

本文件由 `SKILL.md` §1 在**落盘失败**或**图片可能含敏感信息**时引用。主路径（成功
落盘）的四步命令在 `SKILL.md` §1 里是自包含的，不需要先读本文件。

所在仓库：`claude-devkit-marketplace`；本文件属于 `plugins/task-keeper/skills/tk-debug/references/`。

## 1. 两条不可让渡的约束（先理解，再照做）

### 1.1 只有主会话能落盘，派出去的 subagent 不能

用户贴的图在数据结构里是这样的（transcript 实证）：

```
image block 键 : ['source', 'type']
source 键      : ['data', 'media_type', 'type']
source.type    : 'base64'
media_type     : 'image/png'
data 长度      : 187432 字符
```

图片以 base64 形式存在于**主会话的对话流**里，`SKILL.md` §2 派出去做登记+triage 的
subagent 是独立上下文，拿不到这段数据。所以抢救像素只有主会话能做，且必须在派出
那个 subagent **之前**完成。

给模型看到的文本块只是 `[Image #1] <用户的话>` 这样的占位符，磁盘路径由 harness 另行
以 `[Image: source: <绝对路径>]` 的形式给出——两者是不同的东西，不要混。

### 1.2 源路径是会话级临时资源，随时失效

实测 `~/.claude/image-cache/` 的状态：

```
session 子目录数: 1
图片文件总数: 1
/Users/<me>/.claude/image-cache/<当前session-uuid>/1.png

已清理: 46e71d0b-c136-4378-b07c-120de501b482   ← 另一个会话，整个目录消失
已清理: 524713e1-ab49-43cd-96b2-50e113fa42f3
```

**只保留当前活跃会话的目录**，其余全部清理。而 debug 队列的设计前提是跨 session
持久（等用户 accept、reopen 重修、收官时推迟到下次交付，登记与实际修复隔几天是正常
状态）。两者生命周期不匹配，所以：

- 队列里任何指向 `image-cache` 的路径，**在下一个会话必然 404**
- 即使在同一会话内，路径也可能已经失效——已实测的案例：某会话 AI 上一轮宣布
  「截图先落盘」并执行了 `cp`，下一轮才发现 `image-cache/46e71d0b-…/2.png` 在磁盘上
  已不存在，`cp` 静默失败没被察觉

**结论：只看 `cp` 的退出码不够，必须回读验证目标文件真实存在且非空。**

## 2. 源路径只能照抄，禁止按规律合成

正确来源只有一个：消息里 `[Image: source: /Users/<me>/.claude/image-cache/<session-uuid>/<序号>.png]`
这段 `source:` 后面的原文。

**禁止**按 `image-cache/<session-uuid>/<序号>.png` 的规律自己拼。规律确实很好猜，但
猜出来的路径有两种必然失效：这个会话根本没贴过图（整个 session 目录不存在），或者
序号猜错（序号是会话内计数，不是全局的）。

合成路径的危害特别隐蔽，值得单独记住：假路径一路写进 issue 的「证据」章节，后续
会话打开发现读不到图，**把成因说成「原图被临时目录清理了」，而真相是这个路径从未
存在过**——排查方向就此被带偏，同一个坑会反复出现。这是 DBG-006 的成因。

消息里没有 `source:` 原文时（例如用户在同一轮里追加的图），按顺序处理，一步都不能跳：

1. `ls` 枚举 `~/.claude/image-cache/`，看真实存在哪些文件。**不要挂 `2>/dev/null`**
   ——task-keeper 的 PreToolUse hook 会直接拦截这个组合，因为它会吞掉「目录不存在」
   的报错，让空结果被误读成「确实没有图」。
2. 用 `Read` 打开候选图，**确认内容与用户描述一致**，才可以采用。
3. 仍不确定就请用户重发，不要挑一个最像的用。

## 3. 落盘失败时的兜底（按顺序尝试）

### 3.1 兜底一：从系统剪贴板抢救（macOS，已实测可行）

用户刚贴的图通常还在系统剪贴板里，这条路径能拿到**真实像素**，是唯一还能救回原图的
办法。先确认剪贴板里有 PNG：

```bash
osascript -e 'clipboard info'
```

输出里出现 `«class PNGf»` 才继续；没有就直接跳到 3.2。提取时**只读剪贴板、不修改**：

```bash
osascript <<'AS'
set imgData to the clipboard as «class PNGf»
set fileRef to open for access POSIX file "<目标绝对路径>" with write permission
set eof fileRef to 0
write imgData to fileRef
close access fileRef
AS
```

实测结果（一次真实抢救）：

```
落盘成功: 335714 bytes
文件类型: PNG image data, 2298 x 1088, 8-bit/color RGBA, non-interlaced
```

抢救成功后**仍要走回读验证**（`[ -s "$DST" ]`）。

局限，必须清楚：只对**最后一次复制的内容**有效；用户在贴图后又复制过别的东西就取不到；
用户一轮里贴多张图时只能救回最后一张。所以它是兜底，**不能替代第一时间落盘**。

`pngpaste` 不一定装了（本机实测未安装），不要依赖它；`osascript` 是 macOS 自带的。
非 macOS 环境没有等价方案，直接走 3.2。

### 3.2 兜底二：文字转录（无条件都要做，不只是兜底）

你能看到图，把图里的可见信息逐字写进 §2 派发 intake subagent 的 prompt：

- 报错文本**原文**（不要转述，逐字抄）
- 涉及的页面标题 / 菜单路径 / 按钮文案 / 字段标签
- 错位或异常的具体元素，以及它相对于什么错位
- 期望效果（用户说的「应该怎样」）
- 图上可见的数值、序列号、状态标记

**即使落盘成功也要做这一步。** 理由有两条：fixer 读文字比读图快，不必先 `Read` 一张
大图；且图仍可能因为别的原因读不到（权限、路径含非 ASCII 字符、worktree 隔离），文字
是唯一不会丢的信息。

两条兜底都用不上时（无剪贴板且图内容无法辨识），在 prompt 里明确写
「**原图未落盘，原因：<具体原因>**」。**绝不要留一个几天后必然 404 的假指针**——那比
不留更糟，它会让后续会话误以为「有图可看」，并把排查方向带偏。

## 4. 脱敏：AI 打不了码，所以规则是「不落盘」

`.keeper/<交付id>/debug/<DBG-id>/`（v4 布局下截图与 `issue.md` 平铺同一目录，不再
有独立的 `attachments/` 子目录）里的截图本身**不进 git 历史**——v4 起 `.keeper/`
目录树已整体入库（`index.md` / `issue.md` / `item.md` 等队列文本都被跟踪），"不
入库"这条改由 `.gitignore` 的两条规则单独保证：`.keeper/**/*.png`、
`.keeper/**/*.jpg`（v3 时是整棵 `.keeper/` 整树忽略，规则更粗）。脱敏判据不因此
放松——文件仍然会长期留在磁盘上，可能被其他工具打包、被误 `cp` 出去共享，或在
这两条 gitignore 规则被调整时被一并纳入历史。

落盘前先看一眼图，出现下列任一样就**不要落盘**：

- token / cookie / 密码 / 密钥
- 手机号 / 邮箱 / 身份证 / 员工工号
- 真实客户机构名称
- 产线金额 / 成单数据 / 用户明细

**处置方式不是「打码后落盘」。** AI 没有图像编辑能力，做不到打码或裁剪——把这写成
指令等于要求执行一个不可能的动作，实际结果是 AI 要么忽略这条规则直接落盘（泄漏），
要么卡住不动。正确处置是三步：

1. 跳过落盘
2. 只做 3.2 的文字转录，转录时把敏感值本身替换成 `<脱敏>`，保留排查需要的结构信息
   （例如「手机号字段显示为 `<脱敏>`，格式为 11 位且中间四位未打码」这类描述本身
   不含敏感值，但足以说明 bug）
3. 在 prompt 里写「图含敏感信息未入库，如需入库请自行打码后重发」

拿不准是否敏感时**按敏感处理**——bug 截图要证明的是「界面错在哪」，文字转录通常够用。

## 5. 为什么落进 `_inbox/` 而不是 `<DBG-id>/`

落盘发生在主会话，而 `DBG-id` 由 `SKILL.md` §2 派出去的 intake+triage subagent
分配——`.keeper/<交付id>/debug/<DBG-id>/` 这个条目目录（`issue.md` 所在处）是
单一写者（single writer）模式，只有那个 subagent 能建、能写。hook 注入体里那个
「下一个可用 id」是给它用的；主会话拿它自行预分配就出现了第二个写者，两边都可能
用同一个 id。

所以主会话只负责抢救像素、放进收件目录：

```
.keeper/<交付id>/debug/_inbox/<时间戳>-<序号>-<简短说明>.png
```

intake+triage subagent 在登记时分配 `DBG-id`、`mv` 到
`.keeper/<交付id>/debug/<DBG-id>/`（v4 布局下截图与 `issue.md` 平铺同一目录，
不再有独立的 `attachments/` 子目录），并把仓库相对路径写进 `<DBG-id>/issue.md`
的「证据」章节。格式见本目录 `queue.md` §2。

文件名带时间戳是为了避免撞名（同一分钟内多次贴图用序号区分）。文件名尽量用 ASCII：
macOS 的 NFC / NFD 差异会让含中文的路径在「一边来自 git 输出、一边来自磁盘枚举」的
比对里静默匹配不上，这个坑在对账侧已经吃过一次。
