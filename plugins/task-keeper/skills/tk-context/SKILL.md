# tk-context：动手前的上下文收集通道

## 0. 这条通道要防的那件事

某次交付的事后归因里，最大的一类是「**规格写了，但没照着做**」——55 条、占 27.9%。
根因不是能力问题：**实现只看了原型，那几份文字规格 md 没人读，整片规格就此失效**。

它此前不可见，是因为台账记的是「什么坏了、怎么修的」，不记「规格上原本怎么写」。
上游也没兜住：ai-sdlc 的三道机械硬闸基线全是原型 html，覆盖文字规格的 `spec-sync-audit`
轴是 advisory 不阻断、且明文排除 UI 元素——**UI 文字规格在整条链路里唯一被校验的是
「原型存不存在」，不是「原型内容忠不忠于它」**。

本通道的对策**不是保证遵守，是让不遵守可见**：动手前把约束一条条排成表，实现完再逐行核。
保证遵守做不到（没有机械判据能判「这段代码是不是符合这句中文规格」），而让不遵守可见做
得到——只要那一行留在表上是空的。

## 1. 什么时候用

| 场景 | 用不用 |
|---|---|
| 用户说要做 X 功能 / 改 Y，尚未动手 | ✅ 入口 A，主会话派 context-keeper |
| debug-keeper triage 完、派 fixer 前 | ✅ 入口 B，由它自己转 |
| 改错别字、调格式、加日志、重命名局部变量 | ❌ 不用 |
| 纯技术债（重复代码、补测试），无业务规格可对照 | ❌ 不用 |
| `difficulty: easy` 且 `spec_status: violation` 已有明确规格锚 | ❌ 规格已在手，不必再收 |

**两个入口都不自动触发。**「这次动作算不算一个功能单元」是语义判断，做不成机械闸——
硬做只会得到一道靠关键词猜的闸，误杀与漏放同时发生。

## 2. 何为「一个功能单元」

这是派发前唯一需要主会话拿捏的判断。判据一句话：

> **共享同一份规格来源、且必须一起验证的那组断言 = 一个功能单元。**

「必须一起验证」是要害。31 条错误提示文案共享同一份需求表格、少一条就是没做完 →
**一个单元、31 条断言、销账表 31 行**，不是 31 个单元。反过来，「导入校验」与「导出格式」
各有各的规格来源、各自验各自的 → 两个单元，即使在同一个页面上。

拆错的两种代价不对称：

- **拆太细**——同一份规格被切成 N 份分别收集，每份都只看到自己那一角，跨条目的矛盾没人
  发现。成本是重复劳动 + 漏掉冲突。
- **拆太粗**——一个包裹住半个模块的「单元」，断言上百条，销账表没人填得完，最后整张表
  空着交回来。成本是**整条机制空转**，比不做还糟——因为留下了「做过了」的痕迹。

拿不准时**偏细**：两个包可以合并阅读，一个填不完的表救不回来。

## 3. 怎么派

派 `task-keeper:context-keeper`（常驻 keeper，`model` 必须 `"opus"`，`name` 形如
`opus-context-keeper-3f7a`）。派发前先读 `.keeper/<交付id>/.keeper-instance.json` 拿当前
实际 name，读不到才是首次派发。

prompt 里给全四样，缺一样它就得回头问你：

1. **单元边界**——按 §2 判出来的那组断言是什么，用一句话说清「这次要做的是什么」
2. **用户原话**——逐字，不要转述。截图给**绝对路径**，它会自己 `Read`
3. **仓库绝对路径**，以及这是 `implement` 还是 `debug` 阶段（决定要不要做同构扩散面）
4. **已知的锚点**——已经知道的需求文档路径 / DBG 编号 / ontology slug，有多少给多少。
   给不出也行，它会自己找；给了能省它一路盲扫

## 4. 它怎么收（一句话版）

**五方并行、相互印证**：需求 / 原型 / sdlc spec / ontology / 代码，同批并发派五个只读
`Explore`，回来后做归一与印证矩阵。

**不走「ontology 为主入口」**——那等于让一个未经确认的中间层决定该看什么，它漏收的元素
会静默传播成「查过了、没有」，且全程无信号。ontology 是**第四个平等信源**，不是索引。

**涉及其他领域知识、读不到代码时降级为三方**（需求 / 原型 / ontology），且降级必须落在
产物的 `sources` 字段上——参与方数量要可见，不能埋在正文里。

完整判据（各路的停止条件、归一锚点优先序、矩阵每格怎么填、不一致四态、同构扩散面）见
`references/collect.md`。产物长什么样、谁填哪一份见 `references/artifacts.md`。

## 5. 产出什么，怎么用

```
.keeper/<交付id>/context/CTX-001/
├── context.md      ← 上下文包 + 印证矩阵      （keeper 写）
├── ledger.md       ← 空销账表                  （**实现者填**）
└── reconcile.md    ← 事后差异核对              （keeper 写）
```

主会话拿到包之后：

1. **先看回执里的「歧义登记 open 几条、其中矛盾态几条」**。有未决矛盾态就先拍板，
   不要让实现者去猜——猜出来的那个选择日后没人知道是猜的。
2. **把 `ledger.md` 的路径交给实现者**（ai-sdlc 的 implement 流程 / debug 的 fixer），
   要求逐行填「实现位置 `file:行号`」与「状态」。
3. **实现完成后再唤醒 keeper 跑事后核对**。这一步不自动，得有人叫。不跑核对，销账表就
   只是一份自我声明——而自我声明正是本通道要防的那个东西。

## 6. 职责边界（本插件不做什么）

**只负责上下文收集与汇报，不参与实现。** 具体四条：

1. **不写业务代码。** 实现是 ai-sdlc 的 implement 或 debug 的 fixer 的职责。
2. **不拦截、不阻断任何流程。** 判据：**产物存在与否，不改变 ai-sdlc 任何一步的行为。**
   这是唯一不会让两套流程互相甩锅的形态。
3. **不写 `sdlc/` 下任何文件，`sdlc/ontology/` 尤其不写。** ai-sdlc 有自己的收口闸与
   sync 脚本，从旁边写进去会与它打架。发现 ontology 漏收，写成建议留在包里。
4. **不填销账表的状态列、不催填。** 填表的必须是写代码的那个人——否则就成了自己印证自己。

## 7. 与另两条队列的关系

| 队列 | 管什么 | 与本通道的接点 |
|---|---|---|
| `debug` | 已经坏了的东西 | triage 完派 fixer 前请出包（入口 B）；`spec_status` 的规格溯源是**诊断侧**，本通道是**预防侧**，同一件事的两端 |
| `chore` | 杂务、台账、沉淀 | 收集中判出的**规格空白**（八类来源全查无表述）转 chore，摘要写「待产品确认 X 的语义」，**不派 fixer** |

规格空白不能派实现者去「修」——空白无从判对错，派去只会凭直觉补一个同样没人确认过的行为，
**把空白伪装成已定案**。原先可见的未知就此变成不可见的错误前提。
