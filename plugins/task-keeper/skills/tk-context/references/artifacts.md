# 产物三件套：`context.md` / `ledger.md` / `reconcile.md`

收集手法见 `collect.md`。本文件只管**产物长什么样、谁写哪一份、怎么填才算合格**。

## 0. 目录布局与「三份分开」的理由

```
.keeper/<交付id>/context/
├── index.md                ← hook 每轮重算的派生视图，不要手改
├── CTX-001/
│   ├── context.md          ← 你（context-keeper）写。上下文包 + 印证矩阵
│   ├── ledger.md           ← **外部实现者填**。销账表，你只负责排好行、留空状态列
│   └── reconcile.md        ← 你写。事后差异核对结果
└── archive/<批次>/CTX-NNN/
```

**为什么销账表单独一份**：它要交给**别人**（debug 的 fixer、或 ai-sdlc 的 implement
流程）写。混进 `context.md` 里，别人填写时会碰到你的产物，回收时分不清哪些行是他改的、
哪些是你原来就写的。这与 debug 队列把 `issue.md`（keeper 写）与 `receipts.md`（fixer
写）分开是同一个道理，不要合并。

## 1. `context.md`

### frontmatter（只放能被机械消费的状态，共 10 键）

```yaml
---
id: CTX-001                 # 与目录名一致
summary: 导入模板的错误提示与权重快照   # 一句话，index.md 直接用
status: open                # open | done ← 只有两个。done 表示已跑过事后核对并收口
stage: debug                # implement | debug ← 决定要不要做同构扩散面
about: DBG-017              # 对应的工作单元：DBG-NNN / task id / feature 名
sources: 5                  # 实际参与印证的信源数，只能是 5 或 3（见 collect.md §2）
assertions: 31              # 断言条数 = ledger.md 的行数
inconsistent: 4             # 四态里非「一致」的条数
created_at: 2026-08-10
external_ref: TRACKER#644168   # 可选
---
```

`sources: 3` 是**降级信号**，让它出现在 index 的一列里，是为了让「这份包只有三方印证」
一眼可见，而不是埋在正文某段话里。`inconsistent` 同理——它是本包最有价值的那个数字。

**不要往 frontmatter 加的东西**：任何超过一行的文本；任何能从 `ledger.md` 数出来的派生值
（已销账几条、还剩几条——那随时会失同步）；「谁在实现」（那由 `git worktree list` 现算）。

### 正文七章（顺序固定）

```markdown
# CTX-001 · <单元名，写当前事实>

## 0 元信息与完整度

- 适用阶段：debug（对应 DBG-017）
- 参与信源：5 / 5〔或：3 / 5，第 5 路代码未取到，原因：<具体原因>〕
- 断言条数：31，其中不一致 4（缺席 1 / 矛盾 0 / 偏差 2 / 孤证 1）
- 未查的来源与理由（**逐条列，不许静默省略**）：
  - i18n 文案 → 未查，理由：本单元是纯后端校验逻辑，不涉及前端文案

## 1 印证矩阵

<「断言 × 信源」表。每格三选一：命中（带 path:行号）/ 未命中 / 未查+理由。
 禁止留空格——空格分不清「查了没有」与「没查」，而两者含义相反。>

## 2 规格原文摘录

<矩阵里每个「命中」格对应的原文，逐字，禁转述。按断言编号分段，与 ledger 行号对齐。>

## 3 本体锚点

<ontology 元素 slug、类型、一跳邻居、走了几跳。
 needs_human_review: true 或低 ai_confidence 的条目**必须逐条标注「此条未经人确认」**，
 并给出回溯核实的结果（它 ref 指向的原始规格行说了什么）。>

## 4 代码现场

| 关键逻辑 | 坐标 | 这段干什么 |
|---|---|---|
| 导入行校验 | `ImportService.checkRow:210-260` | 逐行校验并收集错误码 |

## 5 上下游影响点

- 上游（改这里会违反谁的契约）：<逐条，带出处>
- 下游（谁在调用）：<逐条，带坐标；追到跨模块/跨服务边界为止，边界外只记调用关系>

## 6 同构扩散面〔stage: debug 才有本章〕

<与本处形状相同的其它位置，逐条坐标 + 判据（为什么判定它同构）。
 三条检索手段的实际结果都要写：BR 的 applies_to / 代码特征串 grep / 规格清单逐行。>

## 7 歧义登记

| # | 项 | 类别 | 处置 | 状态 |
|---|---|---|---|---|
| 1 | 无等级行是否参与校验 | 矛盾 | 待人拍板 | open |
| 2 | 「合适的宽度」 | 含糊 | 按同项目先例收敛为 480px，已声明 | closed |
| 3 | 版本号何时自增 | 空白 | 待产品确认 | open |

<三类的处置完全不同，不许碾平：
 矛盾 → 必须人拍板，拍完给被推翻那份加覆盖标注；
 含糊 → 可按既有先例收敛，但必须显式声明「我按 X 解释了」；
 空白 → 问产品，**不许自己补**。>
```

## 2. `ledger.md`（你排行，别人填）

排好行、留空状态列，随包一起交出去。**你不填状态列，也不催别人填**——本插件不参与
实现（见 `SKILL.md` 的职责边界）。

```markdown
---
id: CTX-001
about: DBG-017
assertions: 31
filled_by:                  # 留空。实现者填自己的标识
filled_at:                  # 留空
---

# CTX-001 销账表

逐行填「实现位置」与「状态」两列，其余列不要改。

| # | 约束 / 影响点 | 判据（怎样算做到） | 实现位置 `file:行号` | 状态 | 备注 |
|---|---|---|---|---|---|
| 1 | 错误提示 E001 文案 | 与 `req.md:90` 逐字一致 | | | |
| 2 | 错误提示 E002 文案 | 与 `req.md:91` 逐字一致 | | | |
| … | | | | | |
| 31 | 错误提示 E031 文案 | 与 `req.md:119` 逐字一致 | | | |

状态列取值：`已实现` / `未实现` / `不适用`。后两者**必须在备注里写理由**。
```

### 排行的四条硬纪律

1. **行数 = 断言条数**，且必须等于 frontmatter 的 `assertions`。规格是一张 31 行的表，
   销账表就是 31 行——**不许合并成一行「按需求文档的表格实现」**。已实测的事故：报告里
   只提了 1 条，按「现象消失」口径修完即收工，剩下 30 条原样落空。
2. **每行必须有可判真假的判据**。写「实现导入校验」不算判据，写「与 `req.md:90` 逐字
   一致」才算。判据写不出来，说明这条断言没归一好，回 `collect.md` §3 重做。
3. **「实现位置」列不接受「已实现」三个字**，必须是 `file:行号`。这一列是防「形似而神
   不似」的唯一手段——让人能点进去看那到底是不是规格说的那件事。
4. **不许你自己预填任何一行的状态列**。预填等于替实现者做了声明，而你并没有看过他的
   代码；事后核对时你还会拿这份表当基线，等于自己印证自己。

## 3. `reconcile.md`（事后差异核对，你写）

**时机**：实现完成之后。由调用方（主会话或 debug-keeper）唤醒你来跑，不自动。

**做什么**：拿 `ledger.md` 里实现者填的每一行，**回到代码里核实一遍**，把差异汇报出来。
核对**仍然只是汇报，不是实现**——发现没做到的，你不去改，写进差异清单交回调用方。

```markdown
# CTX-001 事后核对（2026-08-10）

- 销账表 31 行：已实现 28 / 未实现 2 / 不适用 1
- 核实结论：**28 行中有 3 行经核实不成立**

## 差异清单

| # | 实现者声明 | 核实结果 | 证据 |
|---|---|---|---|
| 7 | 已实现 `ImportSvc:233` | **不成立**——该行实现的是 E010 不是 E007 | `ImportSvc.java:233` |
| 12 | 已实现 | **不成立**——填的位置不存在该逻辑 | 已 Read，`:180-200` 无相关代码 |
| 19 | 不适用（理由：该场景不会发生） | **存疑**——`entities.md:44` 明确要求该场景 | `entities.md:44` |

## 未填写的行

<销账表里状态列为空的行号。空行不等于未实现，只等于「没人声明」——但这本身要汇报。>
```

**三条核对纪律**：

1. **逐行核，不抽查。** 抽查会让「哪几行被核过」变成不可知，而这正是整套机制要消除的
   那类不可见。
2. **不成立的判定必须给证据**，形态与 ledger 同——`file:行号` + 你实际读到了什么。
3. **状态列为空的行单独列出**，不要与「未实现」合并。空 = 没人声明，未实现 = 有人声明
   了没做，两者的后续动作不同。

## 4. `status` 何时翻 `done`

`open` → `done` 的唯一判据：**跑过一次事后核对，且 `reconcile.md` 已落盘**。

不接受的翻转理由：「实现者说做完了」（那是他的声明，不是核对）、「挂太久了」（挂久不
改变它没被核对这个事实）、「差异清单非空但都是小问题」（差异归差异，核对跑过就算 done，
差异的处置由调用方决定，不影响本包收口）。
