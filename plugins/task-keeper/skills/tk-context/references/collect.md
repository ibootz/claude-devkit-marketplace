# 五方并行收集与相互印证（context-keeper 的核心手法）

本文件是 `context-keeper` 收集阶段的完整判据。产物模板见 `artifacts.md`。

## 0. 为什么是五方并行，而不是「选一个主入口沿边展开」

设计过程中先后否掉过两个方案，理由要记住，否则后来人会再提一次：

**否掉「八维度盲扫」**——维度之间没有交叉验证，每一维扫完只知道「我找到了什么」，
不知道「我漏了什么」。而漏检是静默的。

**否掉「ontology 为主入口、沿边展开」**——ontology 自带 `needs_human_review` 与
`ai_confidence` 字段，说明它本身是抽取产物、其中相当一部分未经人确认。拿它当唯一入口，
等于**让一个未经确认的中间层决定该看什么**：它漏收的元素，沿边永远走不到，且没有任何
信号提示你走漏了。这与本机制要防的那个病根同形——只看原型不读文字规格，也是信了一个
中间层。

**五方并行的价值不在「更全」，在于不一致本身就是产出。** 五个信源各自独立到达同一个
事实：一致，则该事实置信度高；不一致，则这个不一致**恰好指出了规格漂移 / ontology 过期
/ 实现偏离发生在哪一层**。矩阵里的空格与冲突比命中更有价值。

## 1. 五路分片

五路的检索手法互不相同、输入互不依赖，所以**必须同批并发派发**——一条消息里发五个
`Agent` 调用，`subagent_type` 一律 `Explore`（只读），`model` 从 `sonnet` 起。

| 路 | 信源 | 停止条件（写死进 prompt 的【约束】段） |
|---|---|---|
| 1 需求 | 需求文档、产品文案、用户原话 | 追到本功能单元直接涉及的章节为止，不追整份文档的其余部分 |
| 2 原型 | `*.prototype.html` / `*.proposal.html` / upstream demo | 只看本单元对应的那一个页面（含其 MOD 红点段），不遍历同目录其它页面 |
| 3 sdlc spec | `contracts.md` / `entities.md` / `behaviors/*.gherkin` / `ui/views/*.md` | 追到本单元命名的 feature 目录边界为止，不跨 feature |
| 4 ontology | 13 类元素目录 + 双向边 | **一跳邻居**为默认；`type: mutation` 的 action 或 P0 缺陷放宽到两跳，写明实际追了几跳 |
| 5 代码 | 方法级实现与调用链 | 追到跨模块 / 跨服务边界为止；边界之外只记「调用了谁」，不进去读 |

### 1.1 需求路

读需求原文，**逐字摘录**要落进产物的那几段，不要转述。同时记下：这份需求里有没有
表格 / 编号清单 / 枚举——**那些是最容易整片落空的形态**（一张 31 行的文案表，实现方
只做了报告里提到的那一条，剩下 30 条静默落空，是已实测的事故）。表格与清单必须**按行
展开成断言**，不许压缩成一句「按需求文档的表格实现」。

### 1.2 原型路

原型有三个来源，**都要查、都要记结果**（命中与否都写）：

```
sdlc/backlog/{feat-*}/upstream/*.html                        # 上游产品/设计交付的 demo
sdlc/specs/features/{feature}/ui/views/{page}.prototype.html  # define 阶段生成的真原型
sdlc/deliveries/D-*/ui/{page}.proposal.html                   # 既有页面的演化提案（读 MOD 红点段）
```

**本路的关键判据：原型命中不等于规格命中。** 第 2 路命中、第 3 路（view spec）未命中时
必须显式标注——这正是「文字规格写了、只是没画进原型」那类偏差的信号，且它在上游的机械
闸里是穿透的（那些闸的基线全是原型 html）。**只查了原型就写「规格已确认」是不合格的
收集。**

### 1.3 sdlc spec 路

```
sdlc/specs/features/{feature}/_index.md          # 不变量表，先读它定位
sdlc/specs/features/{feature}/contracts.md       # API 契约
sdlc/specs/features/{feature}/entities.md        # 实体与字段约束
sdlc/specs/features/{feature}/behaviors/*.gherkin # 行为语义
sdlc/specs/features/{feature}/ui/views/*.md      # view spec（文字化的交互元素表）
sdlc/specs/concepts/<entity>.md                  # 概念词典
sdlc/deliveries/D-*/decisions.md                 # 交付级决策
```

**注意**：业务包常是独立 git 仓库，`sdlc/` 住在**上层工作区根**。本仓找不到就上溯一层，
不要因为「当前目录没有 sdlc」就判定这个项目没有规格。

### 1.4 ontology 路

**先分清是哪一个 ontology，两者同名但完全不同，读取入口不能写成一个路径常量**：

| | 路径 | 是什么 |
|---|---|---|
| 业务仓本体 | 仓根 `sdlc/ontology/` | 每个业务仓自己维护的、面向调用方的全局单体契约库 |
| aPaaS 平台本体 | `codifiedcontext/ontology/`（随 `cctx-dev-apaas` 插件分发） | 只描述 aPaaS 平台自身的端点契约 |

判据：做业务仓内部的功能实现或缺陷修复 → 前者；调 aPaaS 平台 API → 后者。

**结构事实（实测）**：`sdlc/ontology/` 是**嵌套 submodule**（work 仓 → `sdlc/` →
`ontology/`），按 13 类元素分目录，不按 feature 分区，各子目录带自动生成的 `_index.md`。
实测某仓规模：`action-types` 703 个、`business-rules` 120 个、`object-types` 105 个。

检索顺序：

1. 读目标子目录的 `_index.md` 定位 slug，**不要 glob 整个目录**（几百个文件）
2. `Read` 命中的单个元素文件
3. 沿边展开一跳：

| 从 | 沿哪条边 | 到 |
|---|---|---|
| `object-type` | `## Action Types` 表 | 操作该对象的全部 action |
| `action-type` | `patient` 字段 | 它操作的对象（反向边） |
| `object-type` | `## Business Rules` 列表 | 约束它的 `BR-*` |
| `BR-*` | `applies_to[]` | **引用这条规则的全部 action** ← 同构扩散面的现成坐标 |
| 任一元素 | `source_invariants[].ref` | **规格文档的具体行** |
| 任一元素 | `## Code Evidence` / `source_ref` | **业务代码的 `path:行号`** |

后两条是 ontology 最有价值的地方：它一端连规格行、一端连代码行。**但拿到这两个指针后
仍要交给第 3 路与第 5 路去独立核实**，不能直接采信——那样就退回「主入口」模式了。

**本路的强制标注**：引用的元素若 `needs_human_review: true` 或 `ai_confidence` 偏低，
**必须在产物里标注「此条未经人确认」并回溯它 `ref` 指向的原始规格行**。理由：这是规格
空白的第三种形态——不是「什么都没写」，而是**看起来有权威记录、实则是 AI 抽的且没人
确认过**。照单全收会把一个推断当成产品定义。

### 1.5 代码路

产出必须到**方法级 + 行号范围**，只给文件名等于没给：

| 要素 | 形态 |
|---|---|
| 关键逻辑落点 | `Class.method:120-158` + 一句话说明这段干什么 |
| 上游 | 谁的契约会因为改这里而被违反 |
| 下游 | 谁在调用它（追到跨模块 / 跨服务边界为止） |
| 同构点 | 与本处形状相同的其它位置，逐条坐标（见 §6） |

项目若已建 codegraph（见 `devkit-tool:codegraph-index`），符号与调用边检索优先走它，
比 grep 省 token；没建就用 `grep -n` + `Read` 定点。

## 2. 三方降级（涉及其他领域时）

第 5 路（代码）取不到的场景是闭集：代码不在本仓、属于别人的服务、属于外部平台。此时
退化为**三方并行（需求 / 原型 / ontology）**，并在产物里逐条标注：

> **本项仅三方印证，置信度低于五方。**

**不标注就是错的**——后来人会把三方结论当成同等强度的依据。三方场景下 ontology 路的
权重反而上升（它是唯一能描述外部契约的信源），所以 §1.4 那条「未经人确认必须标注」在
三方场景下更要严格执行。

## 3. 归一：把五路结果对到同一批断言上

**印证的单位是「断言」，不是「文件」。** 五路收完必须先归一，否则矩阵会变成五列各说
各话。同一个事实在五方的叫法通常不同——需求叫「错误提示文案」，ontology 叫
`error_codes`，代码里是某个 `ErrorMsgEnum`。

**归一锚点的优先序（取第一个能取到的，不许折中出新名字）**：

1. ontology 的元素 slug 或 `BR-<TOPIC>-<NAME>` id
2. 规格文档里的编号（表格行号、Scenario 名、字段名）
3. 代码标识符原文（类名 / 方法名 / 枚举值 / 常量名）
4. 可见 UI 文案原文

四类都取不到时才由你判断，且**必须在产物里声明「这是我为对齐起的名字，五方来源里都
没有这个词」**。这条与「严禁自造业务名词」同源：归一时只能选五方中某个权威来源的原词，
**不许折中出第六个名字**。

归一是整条流程里最难的一步，也是 `context-keeper` 钉 `opus` 档的理由——归错一次，
下游整张矩阵与销账表跟着错。

## 4. 印证矩阵

产物的核心不是五份报告拼起来，而是一张「断言 × 信源」矩阵：

| 断言 | 需求 | 原型 | spec | ontology | 代码 | 判定 |
|---|---|---|---|---|---|---|
| 导入错误提示共 31 条 | 表格给全 `req.md:88-119` | 未画 | 有 `ui/views/pc-import.md:40` | 未收录 | 只实现 3 条 `ImportSvc.check:210-260` | **规格失守** |
| 备注上限 200 字 | 有 | — | 有 | 有 `BR-NOTE-LEN` | 前端无限制 `NoteForm.vue:88` | **偏差** |

每格三种写法之一：**命中**（给 `path:行号` + 逐字摘录放在矩阵下方）、**未命中**、
**未查 + 理由**。**不许留空格**——空格无法区分「查了没有」与「没查」，而这两者的含义
完全相反。

## 5. 不一致四态

| 态 | 形态 | 处置 |
|---|---|---|
| **缺席** | 某方没有 | 先判该方本就不该有（原型不画后端逻辑、ontology 不收 UI 文案）还是真漏了。判「本就不该有」要写理由 |
| **矛盾** | 两方都明确且互相打架 | **必须人拍板**，走待拍板协议。拍完要给被推翻的那一份**加覆盖标注**，否则两份都会被后来人当成有效依据 |
| **偏差** | 同源但细节不同（200 字 vs 无限制） | 最像缺陷的一类，逐条进销账表 |
| **孤证** | 只有一方有，其余全无 | **警惕**：多半是实现自己长出来的行为。若孤证方是「代码」，基本等同规格空白——不许自己补一个「合理」的规格，交产品确认 |

**四态判定不许省略。** 一条断言只要五方取值不完全一致，就必须落到上面某一态，写
「基本一致」不算数。

## 6. 同构扩散面（debug 场景必做，implement 场景不做）

回答的不是「这个功能受什么约束」，而是：

> **与这处缺陷形状相同的位置还有哪些？**

判据是**形状而非语义**：同一个错误写法被复制了几份、同一个校验在几个入口各写一遍、
同一份文案在几处硬编码、同一条 `BR-*` 被几个 action 引用而只有一个做了校验。

三条现成的检索手段：

1. **ontology 边**：该缺陷涉及的 `BR-*` 的 `applies_to[]` 逐条列出了引用它的全部
   action——那就是候选清单
2. **代码形状**：把出错那几行的特征串（方法名、常量、错误码、正则）拿去全仓 `grep -n`
3. **规格清单**：规格里若是一张表 / 一份枚举，逐行核对实现，不要只看报告提到的那一条

**必须在修复之前产出。** 修完再找，改动已经落地、原始形状被破坏了一处，反而更难认。

## 7. 什么时候不必跑满五路

- **第 5 路取不到** → 三方降级，见 §2，须标注。
- **纯样式 / 纯文案的一行小修** → 不必跑本流程（由调用方在派发前判定并豁免）。
- **implement 场景** → 不做 §6 同构扩散面（那时还没有「这处缺陷」）。
- **某一路的信源在本项目根本不存在**（例如项目没建 ontology）→ 那一路照常派出、结果
  记「该信源不存在于本项目」，**不要静默跳过**。跳过会让矩阵看起来是四方一致，而实际
  只有四方参与——**参与方数量必须可见**。

## 8. 检索纪律（两条，撞过才写在这里）

**「没有」是唯一无法自证的检索结果。** 每一路写「未命中」之前，先用一个必然命中的样本
验证检索手段本身有效（同一条命令搜一个你确知存在的符号）。零命中的三种成因——事实如此 /
检索手段失效 / 目标被过滤掉——在屏幕上长得完全一样。

**搜 `worktree/` 里的内容时搜索根必须设进那个 `worktree/`。** 本机 `grep` 被影子成
ugrep 且写死 `--ignore-files`，被 gitignore 的文件是**静默零命中且不报错**。v6 起队列
正文与附件已入库、从仓库根搜正常命中，**仍被排除的只有三类**：`worktree/`、
`.keeper-instance.json`、`.keeper-active`——对它们从仓库根搜必然搜不到，而搜不到与
「不存在」在屏幕上长得完全一样。`Read` 与 `ls` 不走 grep，任何时候都正常。
